## What this proposes

서비스는 정의와 필요한 구현을 리소스 셋으로 묶어 등록하고, 등록 시 이미 가져온 의존 셋까지 함께 검증하고 게시한다. 실행 환경의 여러 View가 저장소를 공유하며, 열린 View가 새 리소스를 쓰려면 서비스가 해당 View에 설정을 적용하고, 컴포넌트 생성은 View 정의의 참조를 따른다. 브라우저에서는 공통 기반이 자식의 배치와 수명주기를 조정하고, 각 연결자가 자기 프레임워크의 인스턴스를 관리한다. 서버에서는 Action을 렌더러 없이 실행할 수 있고, 서비스는 셋이 요구하는 라우팅·데이터·인증 등의 실제 연결을 제공한다. (7–9, 19–21, 25–54, 58–69줄)

## How the existing system works, per this document

현행 Registry는 리소스 정의를 `(kind, id)`로 식별한다. 현재 사용 가능한 API는 호스트 연결 명세를, 구현 상태와 미결 사항은 구현 인계를 참조하도록 되어 있다. DOM과 Svelte가 초기 제공 연결자로 지정되어 있고, 혼합 렌더링의 실행 적합성은 후속 수락 시나리오에서 검증할 항목이다. (3, 19–21, 25, 69줄)

- **Major · 충돌의 식별 기준, 25–28줄.** 25줄은 현행 정의 식별이 `(kind, id)`라고 설명하지만, 27줄은 같은 리소스 ID가 충돌한다고 적는다. 같은 `id`의 Query와 Action을 하나의 저장소에 등록할 수 있는지 두 문장으로는 판단할 수 없다. 리소스 충돌 판정에 `kind`가 포함되는지 명시해야 한다.
- **Major · Headless 등록 단위, 30, 58–60줄.** 논리적으로 하나인 셋에서 서버가 core entrypoint만 가져올 경우, 그 구성을 등록하는 것과 UI 구현 요구가 포함된 셋을 등록하면서 구현을 누락하는 것의 경계가 불명확하다. 등록 검증이 어떤 구성을 입력으로 보는지에 따라 동일한 서버 설정이 등록에 성공할 수도 실패할 수도 있다.
- **Major · 실행 환경과 등록 범위, 27, 34–36줄.** 실행 환경당 저장소 하나라는 규칙에서 실행 환경을 구분하는 기준이 없다. 한 프로세스에 별도로 초기화한 두 호스트가 있을 때, 한 호스트에서 등록한 셋이 다른 호스트의 새 View에 노출되는지와 동일 ID 충돌이 호스트를 넘는지 판단하기 어렵다.
- **Nit · 혼합 트리에서 자식의 정체성, 25, 42, 66–67줄.** 리소스 정의의 식별과 트리에서 이동·교체되는 자식 인스턴스의 식별을 같은 용어로 읽을 수 있다. 같은 Button 정의를 두 번 사용한 경우를 생각하면, 67줄에서 조정하는 대상이 개별 배치 인스턴스인지 짧게 밝혀 주는 것이 도움이 된다.

검토 페르소나와 대상 문서 1–69줄만 읽었다. 문서 안의 링크는 참조 위치로 확인했다.
