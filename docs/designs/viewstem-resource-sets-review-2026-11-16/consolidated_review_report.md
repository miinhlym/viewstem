# Viewstem 리소스 셋과 브라우저 렌더링 · EGM 통합 리뷰

**판정** — 공통 브라우저 기반과 DOM·Svelte 연결자 구조, 실행 중 등록과 View별 명시 적용을 유지할 수 있다. 상세 구현 계획을 확정하기 전에 열린 View의 적용 수명, 저장소 소유와 게시 경계, headless 구성의 합성, slot이 바뀔 때의 자식 수명을 먼저 정해야 한다. 대안의 비용은 이미 결정 이력에서 비교하고 있다. 공통 View 수명 호스트와 core 투영을 재사용할 근거가 있으며, 브라우저에서의 동작과 비용은 후속 검증이 필요하다. [확정 설계](../../spec/12-resource-sets-browser.md) · [결정 이력](../../history/resource-sets-browser-2026-11-16.md#아키텍처-선택) · [구현 인계](../../handoff/resource-sets-browser-2026-11-16.md)

## 구현 계획에 필요한 동작 계약

### F1 · 열린 View의 설정 적용과 여러 표시 연결 — Major

셋 등록과 열린 View에 설정을 적용하는 일은 구분되어 있지만, 적용에 성공한 A의 편집 중 State, 유지 가능한 컴포넌트 인스턴스, 진행 중 실행을 보존할지 새 수명으로 넘길지가 없다. 현행 `updateDefinition()`은 현재 Registry를 유지하고, `replace()`는 최신 Registry로 같은 View의 내부 수명을 바꾼다. 단순 추가를 `replace()`로 구현하면 화면 정의가 같아도 편집값과 기존 실행이 달라질 수 있다. [대상 명세 36–44행](../../spec/12-resource-sets-browser.md#공통-저장소와-view-적용) · [현행 호스트 계약 78–87행](../../spec/07-host-integration.md#최소-sdk와-적용-완료)

**제안** — 추가 적용에서 호환되는 State·인스턴스·실행을 어떻게 다룰지 한 문장으로 정한다. 같은 View를 두 곳에 붙이는 현행 경로도 확인한다. 셋 등록만 끝난 기존 View에 새 연결이 붙어도 해당 View가 보관한 정의·구현·Action 구성을 사용하고, 명시 적용 중 뒤늦은 이벤트가 새 Action과 섞이지 않는 조건을 명시한다. 두 연결은 각자의 DOM 반영·실패·해제를 기존 적용 핸들로 관찰할 수 있다. 수락 사례에서 A/B의 격리, 등록 후 A의 새 연결, A에 연결 두 개가 있을 때의 느린 갱신과 한 연결의 해제를 각각 확인한다. [Svelte의 초기 연결 구성 조회](../../../packages/svelte/src/lib/connection.ts) · [기존 DOM 다중 연결 테스트](../../../packages/ui/test/renderer.test.mjs)

### F2 · 연결자·구현 누락을 어느 단계에서 진단하는가 — Major

설정 준비 실패는 기존 설정을 유지한다. 연결자·구현 누락을 “적용 또는 사용 시” 보고한다는 규칙은 이미 표시해야 할 PlantMap의 구현이 없는 경우에도 어느 결과가 나올지 가르지 못한다. 기존 설정을 유지하고 적용을 거절하는 구현과 새 설정을 게시한 뒤 표시만 실패하는 구현의 관찰 결과가 달라진다. [대상 명세 48–58행](../../spec/12-resource-sets-browser.md#실패-경계)

**제안** — 준비 중 대상 View에 이미 필요하다고 확인할 수 있는 구현이 없으면 적용을 게시하기 전에 거절한다. 적용 후 조건 변경 등으로 처음 필요한 컴포넌트의 누락은 표시 연결의 진단과 완료 결과로 다룬다. 저장소에 있는 미사용 UI는 검사 범위 밖에 둔다. 이미 보이는 노드의 연결자 누락, 나중에 나타난 노드의 누락, 구현이 있지만 mount 중 예외를 낸 사례를 각각 관찰하면 실패 경계를 검증할 수 있다.

### F3 · 저장소 소유와 기존 Registry 게시 경로 — Major

“실행 환경당 하나”가 프로세스·브라우저 컨텍스트와 같은 기술 경계를 뜻하는지, 서비스가 Runtime과 저장소를 조립하는 명시적 소유 범위를 뜻하는지 불분명하다. 현행 `createRuntime()`은 Registry를 만들거나 주입받는다. 같은 프로세스의 두 독립 호스트에서 시작한 등록이 서로 보이는지와 충돌하는지는 어느 범위를 고르는지에 따라 달라진다. [대상 명세 34행](../../spec/12-resource-sets-browser.md#공통-저장소와-view-적용) · [현행 Runtime 생성](../../../packages/core/src/api.mjs)

**제안** — 1차에서 저장소 하나를 세는 소유 단위와 기존 주입 경로의 공유·격리를 먼저 명시한다. 같은 저장소를 쓰는 경우 셋 게시와 현행 직접 등록·교체·resolver 간 충돌을 이행 계획에 넣는다. 예를 들어 resolver가 `createView()`에 필요한 정의를 기다리는 동안 같은 `(kind, id)`가 셋에 의해 게시되면 오래된 후보가 그 정의를 덮지 않아야 한다. 충돌이 관찰되는 경로와 이미 성공한 등록의 보존을 수락 사례에 담을 수 있다. 현행 resolver의 리소스 정의 조회는 이미 import한 셋의 의존 등록과 별개의 경로다. [호스트 확정 경계](../../spec/07-host-integration.md#jsts-호스트-api--d150) · [현행 resolver와 후보 게시](../../../packages/core/src/runtime.mjs)

### F4 · Headless 구성의 등록 단위와 의존 셋 재사용 — Major

논리 셋과 배포 진입점이 분리될 수 있으므로 “등록 전체”가 검증할 대상을 정해야 한다. core 전용 진입점만 가져오는 정상 요청과, UI 구현을 포함한다고 선언한 요청에 구현이 실제로 빠진 경우는 관찰 결과가 달라야 한다. core 구성 다음에 같은 논리 셋의 브라우저 구성을 추가할 때 셋 ID만으로 재사용하면 새 UI를 건너뛸 수 있다. 별도 등록으로 처리하면서 core 정의를 다시 싣는 방식은 의도한 의존성도 중복으로 거절할 수 있다. [원자 등록 계약](../../spec/12-resource-sets-browser.md#셋-식별과-등록) · [Headless 계약](../../spec/12-resource-sets-browser.md#headless-실행과-호스트-기능)

**제안** — 선택한 배포 구성이 등록 대상으로 삼는 정의·구현을 명시한다. 예를 들어 core 구성과 브라우저 확장의 등록 식별자를 별도로 두고, 확장이 같은 core 구성에 의존하게 할 수 있다. 이 방식은 비교용 제안이다. 선택한 모델을 서버의 core 단독 등록, 브라우저 증분 등록, 다이아몬드 의존을 통해 두 구성을 만나는 등록으로 검증한다. 동일 셋으로 인정하는 조건, 호환 불가 버전의 결과, 순환 거절 여부와 진단은 관찰 가능한 계약으로 명시한다. 순회, 저장 형식, 버전 비교 알고리즘은 구현 단계에서 정할 수 있다.

### F5 · 부모 slot이 사라지거나 교체될 때의 수명 — Major

부모와 자식의 DOM 소유권은 정해져 있다. Svelte Layout이 같은 주소·세대의 DOM Button을 유지하며 콘텐츠 컨테이너 자체를 바꾸면, 주소·세대만으로는 Button을 이동할지 다시 만들지 정할 수 없다. 부모의 변경과 자식의 대기 중 mount·갱신이 겹치는 경우에는 cleanup과 완료 대기에도 같은 판단이 필요하다. [혼합 트리 소유권](../../spec/12-resource-sets-browser.md#혼합-트리의-소유권) · [기존 수락 시나리오](../../handoff/resource-sets-browser-2026-11-16.md#후속-수락-시나리오)

**제안** — 첫 범위에서는 일반 콘텐츠 slot을 유지하는 부모를 지원하고, 영역이 철회될 때 자식 정리와 늦은 이벤트 차단을 정의하는 방식이 작다. 교체를 지원한다면 같은 키 이동과 새 마운트를 가르는 조건을 정한다. 양방향 혼합 사례에서 안정적인 slot의 keyed 이동, 부모 제거 또는 slot 철회, 한 번의 cleanup, 해당 갱신의 완료를 관찰한다. 포커스·selection·로컬 상태는 명시한 조건에서 실제 브라우저로 확인한다. 현행 `ViewstemView`의 부모 context 상속과 순수 DOM의 기존 카탈로그 동작은 이행 검증의 기준이다. [기존 Svelte 수명과 context](../../spec/07-host-integration.md#jsts-호스트-api--d150) · [현행 DOM 조정](../../../packages/ui/src/dom.ts)

### F6 · 실행 코드의 신뢰와 호스트 기능 — Major

외부 작성자의 셋과 연결자는 실행 코드를 포함할 수 있다. 예를 들어 모듈 import가 이미 만든 구독은 이후 등록 후보를 버려도 사라지지 않는다. capability 선언이 그 코드를 제한하는지, 서비스가 준비한 기능을 설명하는지 해석이 갈릴 수 있다. 현행 core는 코드 Action을 신뢰된 호스트 코드로 다룬다. [등록 및 원자성](../../spec/12-resource-sets-browser.md#셋-식별과-등록) · [호스트 외부 기능](../../spec/12-resource-sets-browser.md#headless-실행과-호스트-기능) · [현행 코드 Action](../../VIEWSTEM-SPEC.md#73-코드형-action-확장)

**제안** — 외부 실행 코드를 받아들일 주체와 실제 기능 공급·호출 권한을 분명히 하고, 원자성의 효과를 저장소 게시에 한정한다. routing capability를 서비스가 넣어 Action이 호출되는 경우와 필요한 기능이 없는 경우를 수락 사례에 넣는다. 누락을 등록·적용·호출 중 어느 단계로 분류할지는 사용 예시와 함께 결정할 수 있다.

### F7 · 외부 작성자의 공개 계약을 검증하는 소비자 — Major

공식 DOM/Svelte 혼합 사례는 두 패키지의 상호 동작을 확인한다. 양쪽이 비공개 모듈을 공유해도 이 사례는 성공할 수 있다. 제삼자가 공개 계약만으로 쓸 수 있다는 약속에는 별도의 관찰 지점이 필요하다. [공개 확장 목표](../../spec/12-resource-sets-browser.md#제품과-패키지-역할) · [기존 수락 시나리오](../../handoff/resource-sets-browser-2026-11-16.md#후속-수락-시나리오)

**제안** — 배포 패키지의 공개 export만 사용하는 독립 소비자가 작은 셋과 연결자를 작성하고 공식 연결자와 하나의 View에서 섞는 사례를 추가한다. 최소 연결자면 제삼자 작성 경로를 검증할 수 있다. React 제품 구현은 별도 범위다.

## 기존 계약에 맞추는 문구

**F8 · 등록 식별과 상태 표시.** 기존 `(kind, id)`를 충돌 문장에 직접 쓴다. 같은 `summary`를 가진 Query와 Component는 공존하고, 다른 정의가 같은 `(kind, id)`를 차지하면 신규 등록 전체가 거절된다. 정의 ID, 셋 ID, 개별 배치 인스턴스의 식별은 각각 뜻이 다르다. 실패 표의 열 제목에서 보장과 미결을 함께 읽을 수 있게 하고, Svelte와 바닐라 DOM 연결자가 공통 기반을 사용한다고 바로 설명한다. [대상 명세](../../spec/12-resource-sets-browser.md) · [기존 식별 계약](../../VIEWSTEM-SPEC.md#41-정의와-인스턴스)

## 적용 순서 제안

1. F1–F4에서 서비스가 관찰하는 성공·실패와 보존 범위를 사례로 고정한다. F8의 이미 확정된 식별 계약은 이에 맞춰 문구를 정리할 수 있다.
2. F5–F7을 연결자 및 패키지 이행 계획의 수락 기준에 넣는다. 기존 호스트 수명·완료·오류 계약을 기준으로 작은 DOM/Svelte 혼합 사례와 독립 소비자부터 확인한다.
