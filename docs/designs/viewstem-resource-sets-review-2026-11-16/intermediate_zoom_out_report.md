# EGM 8단계 · 구조 재검토

독립 `egm-zoom-out` 리뷰어가 페르소나와 Zoom Out 기준, [대상 명세](../../spec/12-resource-sets-browser.md) 1–69행, 지정 로컬 맥락과 5–7단계 보고서를 읽었다. 대상은 앞선 단계와 같은 내용이다. 리소스 셋을 실행 중 등록한 뒤 대상 View에 적용하는 모델과 공통 브라우저 기반 위의 연결자 구조는 유지할 수 있다는 판단이다. 공통 기반은 주소·세대·순서·slot을 조정하며 기존 Registry 후보 검증·게시와 `createRendererHost` 수명·완료·진단을 재사용할 수 있다.

| ID | 분류 | 8단계 판단 |
|---|---|---|
| Z8-1 | Major | 저장소 소유 단위, 독립·공유 호스트의 가시성과 충돌, 동일 셋 재등장·버전 불일치·의존 순환의 외부 결과를 계획 전에 정한다. 그래프 순회와 게시 알고리즘은 계획에서 다룰 수 있다. |
| Z8-2 | Major | 열린 A의 State·인스턴스·실행 수명과, 동일 View의 여러 표시 연결에서 늦은 이벤트·완료·오류·해제를 어느 적용에 귀속할지 명시한다. 적용 후보에서 확인 가능한 바인딩 누락과 이후 렌더 실패도 구분한다. 등록 뒤 기존 View를 새 표시 대상에 붙이는 사례를 보강한다. 현재 Svelte 연결은 생성 시 렌더러의 어댑터와 Registry를 읽는다. |
| Z8-3 | Major | 부모가 안정적인 slot을 제공한다는 1차 범위를 둘 수 있다. 교체를 지원하려면 slot 철회·재연결 시 자식의 수명과 정리를 정한다. 기존 `ViewstemView`의 부모 context 상속도 호환성 사례에 남긴다. |
| Z8-4 | Major | 호스트가 실행 코드의 신뢰와 실제 기능 공급을 결정한다는 경계와, 저장소 게시 원자성의 범위를 명시한다. capability의 공급·누락을 어느 단계에서 관찰하는지 정한다. |
| Z8-5 | Major · 추가 | 동일 논리 셋의 core 전용 진입점을 먼저 등록한 다음 브라우저 진입점을 가져오는 경우 결과가 비어 있다. 셋 ID만 같다고 생략하면 UI 확장이 빠질 수 있다. 서로 다른 등록으로 처리하되 core 정의를 다시 싣는 경우 중복으로 거절될 수 있다. core 구성과 브라우저 확장에 독립 등록 식별자를 두고 확장이 core를 의존하는 방식은 검토할 제안이다. |
| Z8-6 | Major · 추가 | `resourceResolver`가 `createView` 또는 `replace`에 필요한 정의를 준비하는 동안 같은 `(kind, id)`를 가진 셋이 게시될 수 있다. 기존 resolver의 Registry 게시와 셋 등록이 만나도 부분 변경이나 덮어쓰기가 생기지 않는지 호환 계획에 넣는다. |
| Z8-7 | Nit | `(kind, id)`는 기존 U01에서 확정됐다. 명세 문구와 교차 종류 성공·같은 종류 중복 거절 사례를 맞춘다. 실패 표 제목, Svelte 도입 문장, 정의·인스턴스 용어도 문구 보완 항목이다. |
| Z8-8 | 후속 검증 | 독립 소비자가 공개 export만 사용해 셋과 연결자를 작성하고 공식 연결자와 섞는 사례와 capability 공급·누락 사례를 둔다. 두 혼합 방향의 이동·정리·focus·selection, headless의 실제 import, 기존 소비자 호환은 구현이 생긴 뒤 실행한다. |
