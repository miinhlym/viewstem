# EGM 5단계 · 초기 구조 검토

독립 `egm-zoom-out` 및 `egm-inventive-catalyst` 검토 결과. 두 리뷰어는 각 페르소나와 Zoom Out 기준, [대상 명세](../../spec/12-resource-sets-browser.md) 1–69행 및 지정 로컬 맥락을 읽었다.

| ID | 심각도 | 발견 |
|---|---|---|
| Z5-1 | Major | 명세 36–44·50–51행. 추가된 셋을 열린 A View에 적용할 때 A의 State와 유지 가능한 인스턴스가 새 수명을 시작하는지 모호하다. 현행 `replace()`는 최신 Registry와 새 수명, `updateDefinition()`은 현재 주입 Registry를 사용한다. 기존 편집값과 인스턴스를 관찰하는 수락 사례가 필요하다. |
| Z5-2 | Major | 명세 9·16·19–21·69행. 공식 DOM/Svelte 두 혼합 사례가 통과해도 패키지 비공개 코드에 의존하는 구현을 걸러내지 못한다. 공개 export만 사용하는 독립 소비자가 작은 셋과 연결자를 만들어 섞는 사례가 필요하다. React 구현은 검증에 필요하지 않다. |
| Z5-3 | Nit | 명세 25–28행. 리소스 충돌 기준에 `(kind, id)`를 직접 쓰면 서로 다른 종류에서 같은 문자열 ID를 쓸 수 있다는 현행 규칙이 분명해진다. |
| I5-1 | Major | 명세 25·27행과 인계 45행. 충돌 기준의 두 해석은 등록 성공과 실패를 바꾼다. 같은 ID의 Query와 Component는 함께 등록되고 같은 종류의 중복은 이번 등록 전체를 거절하는 사례가 필요하다. |
| I5-2 | Major | 명세 36행과 인계 46행. A/B는 서로 다른 View다. 현행 호스트는 한 View의 여러 표시 연결을 허용한다. 같은 View를 표시하는 두 연결 중 한 곳의 반영이 늦을 때 이전 구현의 이벤트가 새 적용의 Action과 섞이지 않는지, 완료·오류·해제가 연결별로 어떻게 관찰되는지 정의해야 한다. 기존 `ViewApplication`을 재사용할 여지가 있으며 두 연결의 DOM을 같은 시점에 반영할 필요는 없다. |

공통 브라우저 기반을 쓰면 두 방향의 View 순회와 슬롯 소유권을 별도로 구현하는 비용을 피할 수 있다. 현행 Registry의 후보 검증과 게시, `createRendererHost`의 View 단위 연결·대기·정리, core 투영의 주소·generation·slot을 재사용 후보로 확인했다. 새 작업은 컴포넌트 구현까지 함께 게시하는 경계와 공통 노드 조정에 집중할 수 있다.
