# Viewstem 소비자용 Agent Skills — 독립 검토 후 작업 제안

- 작성자: miinhlym · 작성 지원 및 검토 합성: Codex
- 날짜: 2026-11-05
- 상태: **6개 Goldfish 관점 검토를 반영한 제안. 최종 아키텍처·스킬 구현·배포 결정은 아니다.**
- 원문: [검토 입력 snapshot](review_input_snapshot.md). 검토 절차·지적·읽기 근거는 [통합 보고서](goldfish_review_report.md)를 따른다.
- 이번에 확정된 범위: 외부 소비 프로젝트에서 작업하는 코딩 에이전트를 돕는 스킬 구성 설계. 실제 스킬·도구·제품 코드를 구현하거나 설치·발행하지 않았다.

## 개요

외부 앱의 코딩 에이전트가 설치된 Viewstem 패키지의 공개 API와 JSON 계약을 찾아 앱을 작성하고, 실제 입력·이벤트·상태·수명·화면 동작을 검증하도록 돕는다. 앱의 기존 패키지 관리자와 검사 흐름을 사용하며 Viewstem 저장소를 가지고 있다고 가정하지 않는다.

**단일 `viewstem` 진입 스킬을 작업 가설로 유지한다.** 짧은 진입 지침을 먼저 평가하고, 반복되는 실패를 줄이는 작업별 참조와 읽기 전용 조회 도구를 필요한 만큼 추가한다. 단일 스킬은 설치·선택의 단순성을 위한 초기 선택이며 스킬 효과가 입증됐거나 참조 파일 수와 도구 포함이 결정됐다는 뜻은 아니다.

## 분석

### 원래 가설과 검토 후 요구의 구분

| 항목 | 원래 가설 | 검토를 반영한 제안 |
|---|---|---|
| 진입 | `viewstem` 하나 | 유지. 분리를 정당화할 독립 사용·누락 증거가 생기면 재검토 |
| 보조 도구 | 설치 패키지의 ID별 UI·CEL 계약 조회 | 도구 포함은 평가 대상. UI는 큰 출력에 대해 필드 선택·중복 제거·명시적 생략과 상세 접근을 지원하는 방향(R1) |
| 평가 | 문서와 전체 스킬 비교 | 문서 → 얇은 스킬 → 필요한 참조/도구 추가의 단계적 비교(R2) |
| 진단 | snapshot·진단·최소 재현 | 증상별 공개 채널과 기대/실제 결과 연결(R3) |
| 근거 | 버전/revision/hash 대응 | 조회 결과에 출처·해소한 참조·누락 여부 동반(R4) |
| 발견 | 선택한 부품의 계약 조회 | 요구 → 계열 → JSON/native → 상세의 탐색 연결(R5), 이름 없는 기존 앱 요청의 활성화 평가(R6) |
| 계약 관리 | 원본 스키마·지원 목록 재작성 금지 | codec·uncertain 보존, 원본과 계산 결과 분리, 문서 제약은 대응 자료 연결(R7) |

R1–R7은 [통합 보고서](goldfish_review_report.md)의 요구 식별자다. 원래 제안에 이미 있었던 경계를 새 결함처럼 표시하지 않으며, 검토자의 요구가 제품 계약으로 승인됐다고 간주하지 않는다.

### 필요한 정보로 도달하는 흐름

1. 소비 프로젝트의 위치, 실제 해석되는 Viewstem 패키지와 공개 진입점, 버전 또는 필요한 revision/hash를 확인한다. Viewstem을 쓰지 않는 앱에 도입을 강제하지 않는다.
2. 요청의 작업 경계를 고른다. 작은 수정은 해당 참조로 바로 이동하고 모든 자료를 순서대로 읽게 하지 않는다.
3. UI 작업은 기존 계열 색인 또는 metadata 목록에서 후보를 찾고 JSON/native 지원을 확인한다. 추측한 ID가 없으면 다음 탐색 경로를 안내한다.
4. 설치된 공개 타입·README·지원 metadata와 대응 문서에서 작업에 필요한 계약을 읽는다. 자료가 충돌하면 양쪽 근거와 재현을 남긴다.
5. 소비 앱에서 변경을 적용하고 그 작업의 관찰 가능한 결과를 확인한다. 등록 성공, core 완료, DOM 반영, paint를 서로 같은 증거로 취급하지 않는다.

### 진입 스킬과 참조 자료의 책임

진입 본문에는 사용 조건, 프로젝트·버전 확인, 작업별 참조 선택, 흔한 공통 오류, 결과 검증 흐름만 둔다. 단순한 “폼”, “Svelte”, “Query”라는 단어만으로 넓게 활성화시키지 않으면서 기존 Viewstem 앱의 일반 요청도 발견할 수 있어야 한다.

| 참조 후보 | 담당 작업 | 남겨야 하는 관찰 결과 |
|---|---|---|
| setup | 최초 도입·설치·패키지 선택·core 단독 사용 | 실제 설치와 공개 API를 통한 최소 실행 |
| definitions | View/Component·State/Derived·ports·표현식·when/repeat | 값과 핸들·문맥과 입력·인스턴스와 key 경계 |
| data-actions | Query/Datasource/Variable·Action·URL | 입력부터 조회·상태·동작까지의 연결, 실패·취소·재조회 의미 |
| svelte-host | 마운트·기존 앱 연결·custom adapter·정리 | 계약/구현 등록, emit·slot, 소유/차용 View, 완료 신호 |
| troubleshooting | 출력 누락·값 미변경·stale·취소와 교체 | 실패 경계·공개 진단 채널·최소 재현·기대/실제 결과 |

각 후보는 상세 API 문서의 복사본이 아니다. [현재 문서 지도](../../README.md), [패키지 가이드 구성](../../handoff/docs-package-reference-2026-11-05.md), 공개 패키지 README를 재사용한다. 원문에 기록한 알려진 구현 차이를 모든 버전의 영구 규칙으로 복제하지 않는다.

### 읽기 전용 보조 도구의 조건부 범위

`inspect.mjs`라는 이름은 여전히 후보이며 현재 존재하는 Viewstem CLI가 아니다. 도구를 포함한다면 소비 프로젝트 경로를 명시적으로 받고 공개 파일만 읽는다. 앱 코드 실행·의존성 설치·View 생성·DSL 재검증을 조회와 섞지 않는다.

도구의 목적은 원본 계약에 정확히 도달하는 것이다. 선택 부품의 `mode`, 필수 입력, 원하는 input/event/slot의 스키마·codec·불확실성 표시를 보존하고 공유 참조를 해소한다. 기본 정보와 선택 상세, 전체 원본 접근을 구별하되 숨긴 부분을 완전한 결과처럼 보이지 않게 한다. metadata에 없는 동작 제약은 대응 revision의 문서로 연결하고 수동 지원표로 보충하지 않는다.

조회 결과에는 읽은 패키지·공개 파일·선택 ID와 해당 버전/필요한 hash, 해소·미해소 참조 및 생략 여부를 연결한다. 미설치·알 수 없는 ID·지원 형식 불일치를 구별하고, 직접 JSON 파싱으로 필요한 범위만 읽는 대체 경로를 둔다. 작은 CEL 목록을 같은 도구로 감쌀 필요도 반복 오류·조회 비용으로 판단한다.

현재 metadata를 단순히 펼친 모형에서 Button 하나는 약 42KB, 저장 대화상자 여러 부품은 약 246KB였다. 이 측정은 큰 출력의 위험을 뒷받침하지만 실제 토큰 절감·작업 성공·정확한 출력 상한을 입증하지 않는다. 상세 CLI 옵션과 수치 기준은 후속 설계에서 정한다.

### 문서·버전·배포 경계

정확한 시그니처는 설치된 공개 타입, UI/CEL 가능 범위는 해당 패키지 metadata, 의미 계약은 대응 revision의 명세에서 확인한다. 현재 알려진 명세·구현 차이는 [인계 기록](../../handoff/docs-package-reference-2026-11-05.md#발견한-기존-명세구현-차이)처럼 양쪽을 구별한다. 충돌을 발견했다고 상위 계약을 조용히 바꾸지 않는다.

외부 소비자에게 없는 저장소 `docs/`·test fixture·개인 skill 경로를 필수로 요구하지 않는다. 대응 공개 문서 또는 배포에 포함한 최소 설명으로 필요한 자료 접근을 완결한다. 오프라인 지원과 호스트 지원은 실제 배포물에서 확인한 범위만 선언한다. 관리 원본·배포 채널·host metadata·호환성 manifest는 후속 설계 대상이다. 공개 발행과 지원 상태는 [후속 범위](../../handoff/open-contracts.md#실제-남은-작업)를 따른다.

## 목표와 제외 범위

- 목표: 외부 소비 프로젝트에서 공개 계약을 정확히 찾아 구현하고, 그 요청의 실제 동작을 검증하는 데 필요한 최소 구성을 정한다.
- 목표: 작업별 참조와 도구가 해결한 실패·추가 비용을 구별한다. 효과 없는 요소를 제거하거나 기존 문서로 대체할 수 있게 한다.
- 제외: Viewstem 자체 개발 절차, 실행 중인 서비스에 원격 접속하는 agent API, 권한·서버 연결 제품, 생성기·전체 앱 템플릿·새 DSL validator·별도 MCP 서버의 기본 포함.
- 제외: 이번 설계 작업에서 스킬/도구 구현·설치·발행·제품 변경·사이트 기능 추가. 현재 제품 설계를 재결정하지 않는다.

## 비교할 대안

| 안 | 같은 목표에 대한 이점 | 한계와 선택 근거 |
|---|---|---|
| 문서와 색인만 제공 | 유지 지점이 적고 기존 설명을 사용 | 기준선에서 충분하면 스킬 확대의 근거가 약함 |
| 얇은 단일 스킬 | 작업 선택·근거 탐색·검증 순서를 안내 | 참조/도구 없이 대표 작업에서 어디가 실패하는지 확인 |
| 단일 스킬 + 필요한 참조와 조회 도구 | 반복 오류를 작업 흐름과 정확한 조회로 줄임 | 각 요소의 증분 효과와 출력/호출 비용을 관찰해야 함 |
| core·Svelte·UI별 스킬 분리 | 독립 사용자가 명확할 때 진입점 분리 | 중복·활성화 충돌·형제 스킬 누락 비용이 있음. 이번 검토로 필요성을 입증하지 못함 |

어느 대안도 사용자가 최종 수락·기각한 것으로 기록하지 않는다. 단일 스킬에 누락이 반복되면 분리를 다시 검토하며 스킬 수 최소화 자체를 목표로 삼지 않는다.

## 평가와 다음 단계

원문의 대표 소비자 요청 9개는 [snapshot 116–126행](review_input_snapshot.md)의 기대 동작으로 유지한다. 첫 View, 폼과 Action, core 단독 Query, repeat 정체성, native 요구, 완료 진단, 취소와 늦은 응답, 버전 불일치, 불필요한 도입 방지가 포함된다. 여기에 다음 관찰을 추가한다.

- 여러 부품의 폼·대화상자에서 누적 조회량·중복·잘림·중요 계약 누락을 함께 확인한다.
- 초기 완료 resolve와 queryErrors, core 적용 성공과 renderer 실패를 구분한다.
- 동일한 “필터 추가” 요청을 Viewstem 앱과 일반 Svelte 앱에 주어 활성화/비활성화를 비교한다.
- 조회 결과와 수동 대체 탐색에서 출처·형식 불일치·미해소 참조를 확인한다. 호환성 평가에서 실제 패키지 조합과 스킬 업데이트/복귀 사례도 고려한다.

동일한 패키지·입력·환경·모델 조건을 유지한 새 문맥에서 문서 기준선, 얇은 스킬, 필요한 보강 순으로 비교한다. 모든 조합을 전수 평가하지 않는다. 산출물의 타입·실행·브라우저 동작을 우선하고 API 추측·사용자 수정·파일 읽기·호출·토큰을 함께 기록한다. 평가 반복 횟수와 통과 기준은 실행 전에 정하며 한 번의 성공으로 일반적 효과를 주장하지 않는다.

후속 설계는 최소 진입 본문, 실제 추가할 참조 책임, 선택적 조회의 입출력 경계, 버전 대응, 평가 표본과 통과 기준을 구체화한다. 공개 배포 전에는 저장소 없는 별도 소비 디렉터리에서 상대 참조·공개 패키지·호스트 발견과 도구 실행을 확인해야 한다. 제품 저장소 전용 검사 명령을 소비 앱에 요구하지 않는다.

**현재 완료:** 여섯 독립 관점의 원문 검토와 이 제안의 합성. **아직 미완료:** 스킬 효과 평가·실제 도구 구현·호스트/소비자 설치 검증·최종 구조 결정. 이 제안 자체에 대한 독립 재검토는 실행하지 않았다.
