# Goldfish Review Report — Viewstem 소비자 스킬

- 날짜: 2026-11-05
- 모드: **BRAINSTORM**. 초기 가설의 위험과 대안을 검토했으며 구현 계획 승인·제품 적합성 판정이 아니다.
- 대상: [루트 concepts_brief.md](../../../concepts_brief.md) 전체 138줄. 이후 변경과 구별하는 [검토 원문 snapshot](review_input_snapshot.md)을 보존했다.
- 입력 SHA-256: `ca43013796584231a0e12d6f0ed246c353bea137dbd902c87db574b50f4eef4e`
- 결과: **6/6 completed, not run 0, 실패 0, 재시도 0**.
- 원시 지적: Blocker 0 / Major 3 / Nit 7. 중복 통합 후: **Blocker 0 / Major 2 / Nit 5**.

여섯 검토가 끝난 뒤 주 에이전트가 루트 초안의 진행 상태와 설계 안내를 갱신했다. 이 보고서의 행 번호와 입력 hash는 모두 보존한 snapshot을 가리킨다. 현재 루트 문서에 대한 새 검토 결과로 해석하지 않는다.

단일 `viewstem` 진입 스킬을 분리해야 한다는 근거는 발견되지 않았다. 다만 이것은 스킬의 효과나 최적 구성을 입증한 결과가 아니다. 보조 도구의 범위와 추가 자료의 필요성은 아래 평가로 판단해야 한다.

각 보고서에는 canonical agent ID, 입력 hash, 실제 읽기 목록, 한계를 기록했다. 여섯 에이전트의 실제 `FINAL_ANSWER`를 받은 뒤에만 completed로 집계했다. 진행 메시지를 최종 보고로 대체하지 않았다. [기계 판독 상태 기록](review_status.json)에 같은 식별자를 남겼다.

모든 검토자를 별도 일반 에이전트와 `fork_turns: none`으로 실행했다. 네 슬롯 제약 때문에 독립된 두 명씩 세 묶음으로 실행했고, 뒤 검토자에게 앞선 지적을 전달하지 않았다. 부모 대화 이력을 전달하지 않았다는 뜻이며 파일시스템·호스트 지침·AGENTS.md 격리는 주장하지 않는다. 대화·기억·원문 아카이브는 조회하지 않았다.

필수 읽기는 해당 설치 persona와 대상 문서 전문이었다. 별도의 문서 표준은 공급하지 않았다. 여섯 검토자 모두 전문 읽기와 입력 hash 일치를 보고했다. 추가 근거의 부분 읽기·기계 파싱·검색 결과는 각 보고서에 구별했다. 이 기록은 실제 완료 응답과 읽기 영수증이며, 모든 추가 근거의 모든 행을 별도로 재감사했다는 뜻은 아니다.

## 통합 지적

### R1. ID별 조회도 과도한 출력이 될 수 있음 — Major

- 관점: design 1번, comprehension 1번; zoom-out 2번과 structural 1번을 중복 통합.
- 대상: 원문 38, 81–87, 128행.
- 실패 시나리오: 간단한 폼·대화상자에서도 공통 HTML/ARIA 입력과 DOM 이벤트 계약이 반복되어 필요한 value·payload·제약이 묻히거나 도구 출력이 잘릴 수 있다.
- 요구: 부품 선택 뒤 필요한 input/event/slot을 좁혀 조회할 수 있게 하고, 공통 스키마는 중복을 줄인다. mode·필수 입력·선택 필드의 제약과 codec은 보존한다. 생략 범위와 전체 계약으로 가는 경로를 명시한다. 수동 대체 탐색도 JSON 파서로 출력 범위를 제한한다.
- 평가: 여러 부품을 조합하는 작업에서 누적 출력량, 잘림, 계약 누락, 후속 조회 비용을 함께 비교한다. 짧은 출력 자체를 성공 조건으로 삼지 않는다.
- 반론: ID별 완전 출력도 2.3MB 전체보다 작으며 일부 부품은 1KB 안팎이다. 모든 조회에 복잡한 분할을 강제할 이유는 없다.

### R2. 전체 구성을 한꺼번에 비교하면 불필요한 요소를 남길 수 있음 — Major

- 관점: zoom-out 1번.
- 대상: 원문 15, 50–62, 128행.
- 근거: 현재 평가는 문서 기준선과 스킬 제공 조건을 비교한다. 후자에 진입 지침·여섯 참조 후보·도구가 함께 들어가면 각 요소의 효과를 구별하기 어렵다. 기존 [패키지 문서 인계](../../handoff/docs-package-reference-2026-11-05.md)에 DSL·호스트·수명·UI 조합 가이드가 이미 있다.
- 실패 시나리오: 짧은 진입 지침만으로 개선되었는데 전체 파일 구성과 도구가 필요했다고 판단하거나, 불필요한 조회가 늘어도 어느 요소 때문인지 구별하지 못한다.
- 요구: 문서 → 얇은 진입 스킬 → 관찰된 실패를 해결하는 참조 또는 도구 순으로 비교한다. 추가 요소마다 해결한 실패와 비용 변화를 기록하고 효과 없는 요소는 제거할 수 있어야 한다.
- 반론: 모든 조합의 전수 실험은 비용이 크다. 단계적으로 필요한 요소를 추가하는 비교면 충분하며 범용 평가 기반시설은 필요 없다.

### R3. 초기 완료·core 적용·렌더 성공을 분리해 관찰 — Nit

- 관점: codebase-details 1번.
- 대상: 원문 77, 123–128행.
- 근거: [Core 공개 타입](../../../packages/core/src/index.d.ts)의 `InitialReport.queryErrors`, Store의 `getDiagnostics()`, [Svelte README](../../../packages/svelte/README.md)의 `onError`는 서로 다른 공개 관찰 채널이다.
- 실패 시나리오: `initialComplete` resolve 또는 State 변경만 확인하고 초기 Query나 renderer 실패까지 성공으로 보고한다.
- 요구: troubleshooting에 증상 → 공개 관찰 채널 → 기대/실제 결과를 연결한다. core 적용 성공 후 렌더 실패와 초기 완료 resolve 후 queryErrors가 존재하는 평가를 추가한다. 오류 위치·원인과 인스턴스/세대, 재현 순서를 필요한 범위에서 보존한다.
- 분류 이유: 원문은 진단·최소 재현을 이미 요구한다. 이를 구체화하는 보강이며 새 tracing 체계가 필요하다는 지적이 아니다.

### R4. 계약 조회의 근거와 완결성을 결과에 동반 — Nit

- 관점: codebase-details 2번.
- 대상: 원문 83, 94–96행.
- 실패 시나리오: 같은 버전 문자열의 다른 산출물 또는 수동 대체 탐색에서 어느 계약으로 지원 여부를 판단했는지 재현하지 못한다.
- 요구: 선택 ID, 실제 읽은 공개 파일 위치, 패키지 버전과 필요한 revision/hash, 해소한 참조, 누락·생략 여부를 함께 남긴다. 수동 조회도 같은 근거 수준을 유지한다.
- 분류 이유: 원문에 이미 버전 대응과 hash 확인이 있다. 결과와 근거를 연결하자는 보강이며 전체 manifest 형식이나 로깅 기반시설을 지금 정하자는 요구가 아니다.

### R5. 부품 발견에서 계약 조회까지 연결 — Nit

- 관점: comprehension 2번.
- 대상: 원문 76, 83–85, 122행.
- 실패 시나리오: “검색 가능한 다중 선택” 요구에서 존재할 법한 ID를 먼저 추측하고 큰 지원 JSON을 반복 탐색한다.
- 요구: 요구 → 계열 후보 → JSON/native 지원 → 상세 계약으로 이어지는 경로를 참조 자료에 둔다. 기존 계열 색인이나 메타데이터 목록을 우선 사용한다. 알 수 없는 ID에는 다음 탐색 경로를 제공한다.
- 반론: 기존 문서 색인만으로 충분하면 도구에 검색 기능을 추가할 이유는 없다.

### R6. 일반 표현의 요청도 프로젝트 맥락에 맞게 발견되는지 평가 — Nit

- 관점: comprehension 3번.
- 대상: 원문 66, 116–126행.
- 실패 시나리오: 기존 Viewstem 화면에 “필터 추가해줘”라고 요청했지만 라이브러리 이름이 없어 스킬을 놓친다. 현재 호스트에서 재현한 결함은 아니다.
- 요구: 같은 일반 요청을 Viewstem 사용 프로젝트와 일반 Svelte 프로젝트에 주어 적절한 활성화·비활성화를 함께 관찰한다. 다른 라이브러리 앱에 Viewstem을 불필요하게 도입하지 않는 기존 기준을 유지한다.

### R7. 조회 도구가 별도 의미 계약을 만들지 않도록 경계 보존 — Nit

- 관점: structural 2번.
- 대상: 원문 44, 83–87행.
- 실패 시나리오: 도구의 가공 과정이 codec·uncertain을 지우거나 문서 제약을 수동 지원표로 복제하여 두 번째 계약 관리자가 된다.
- 요구: 원본 metadata와 계산한 표현을 구별하고 codec·uncertain을 보존한다. metadata에 없는 동작 제약은 대응 revision 문서로 연결한다. 출력 축소를 이유로 지원 목록을 손으로 다시 만들지 않는다.
- 분류 이유: 스키마 재작성 금지는 이미 있다. 정확한 출력 의미를 보강하면 되며 범용 해석기를 요구하지 않는다.

## 지적으로 집계하지 않은 판단

[호환성 검토](implementation_readiness.md)는 현재 가설의 버전/revision/hash 대응, 공개 자료 경계, 형식 불일치·대체 탐색이 이미 실패 조건을 다룬다고 판단했다. 실제 해석되는 Core·Svelte·UI 조합과 스킬 업데이트/복귀 사례는 예방적 평가 후보이며 결함 수에 포함하지 않았다. 로컬 조회 스킬에 저장 데이터 마이그레이션·서버 배포·SRE 기반시설을 요구하지 않았다.

스킬 분리, 생성기, 전체 앱 템플릿, 새 DSL validator, 별도 MCP 서버가 필요하다는 근거는 이번 검토에서 나오지 않았다. 도구 자체를 영구 제외하자는 결론도 아니다. 충분한 범위는 실행 평가로 정한다.

## 완성도와 검증 한계

- 미완료 필수 검토는 없다. 여섯 persona와 원문 전문 읽기의 영수증을 받았고 각 최종 응답을 저장했다.
- 지원 JSON의 전체 파싱·출력 크기 측정과 선택 부품 검토가 있었다. 392개 모든 스키마의 의미를 전수 검토하지 않았다.
- 제안 스킬·`inspect.mjs`는 이번 작업에서 구현하지 않았다. 실제 에이전트 성공률·토큰·실행 지연·호스트 발견·설치·업데이트/복귀는 미검증이다.
- 원격 문서 가용성, 과거 패키지 산출물, 실제 외부 소비 프로젝트의 의존성 해석도 이번 검토로 입증하지 않았다.
- 제품/사이트 빌드·런타임 테스트·발행·워크트리 생성은 하지 않았다. 기존 검증 기록은 그 revision의 근거로만 사용했다.
- 수정 [concepts_brief.md](concepts_brief.md)는 원래 가설과 검토 요구를 구분한 제안이다. 모든 검토자는 원문을 검토했으며, 이 수정 제안에 대한 재검토나 최종 승인으로 확대하지 않는다.
