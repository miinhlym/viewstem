# UI 리소스 셋의 작성과 사용 계약 검토

## 검토 질문

기본 UI와 제3자 UI를 선언형 View에서 쓰는 개발자가 컴포넌트 셋 외에 따로 HTML 스타일 범위용 속성을 관리하는 부담을 줄이고 싶다. DOM과 Svelte의 사용 경험이 같고, 셋 작성자가 독립 패키지를 만들어 공개 API로 설치할 수 있어야 한다. 공개 API에서 무엇을 공통화하고 어떤 책임은 패키지 또는 호스트에 둘지 판단한다.

## 현재 동작

- `defineResourceSet({ id, version, dependencies, components })`는 계약·연결자·구현을 등록한다. 의존 셋도 명시적으로 등록된다. Core는 DOM을 가져오지 않으며 JSON View는 이미 등록된 구현을 참조한다.
- `@viewstem/ui`는 `ui` 셋에 DOM 컴포넌트 바인딩을 넣고 스타일을 `@viewstem/ui/styles.css`로 따로 내보낸다. 현재 기본 스타일은 `data-viewstem-ui`가 있는 요소와 그 자식에 적용된다. 빌드가 Basecoat의 루트와 리셋 규칙도 이 영역에 묶는다.
- Svelte에서 독립 화면은 `<ViewstemView {source} resourceSets={[ui]} />`로 만든다. 스타일을 쓰려면 앱이 CSS와 스타일 범위를 제공한다. 공유·대여 표시와 DOM `mount`·`attach`는 외부에서 같은 셋을 등록한다. 각 View는 현재 리소스 스냅샷을 따르며 표시 연결마다 DOM 수명이 있다.
- 기본 UI와 커스텀 Svelte 구현은 같은 View에서 섞일 수 있고 슬롯에 투영된다. 제3자 구현은 네이티브 CSS나 Svelte scoped CSS를 쓸 수 있다. 실제 ViewSpec은 단일 루트다.

## 대안

| 대안 | 소비자 경로 | 책임 |
| --- | --- | --- |
| UI 패키지 내부에서 스타일 범위 관리 | CSS를 한 번 가져오고 `resourceSets={[ui]}`를 사용한다. | UI 구현·CSS가 자신이 만든 DOM과 내장 스타일을 일치시킨다. 일반 셋의 작성 방식은 현재 계약을 유지한다. |
| 브라우저 셋 작성 계약에 스타일 범위 메타데이터 추가 | UI 셋을 등록하면 연결자가 실행 시 스타일 범위를 연다. | 일반 DOM 표시 계층이 셋의 선택적 요구를 적용한다. 코어가 아는 계약과 불투명 구현의 경계를 따져야 한다. |
| 앱 또는 화면의 명시적 스타일 경계 | `ViewstemView` 옵션이나 테마 범위 컴포넌트를 사용한다. | 호스트가 어느 subtree에 테마를 주는지 선택한다. DOM·Svelte 및 독립·대여 화면에서 동등한 옵션이 필요하다. |
| 스타일이 포함된 브라우저 전용 import | 한 import에서 셋과 CSS를 가져온다. | 브라우저 번들러가 CSS 로딩을 맡는다. CSS 매칭 범위와 SSR/Node의 진입점은 별도로 설계한다. |

## 판단 기준

첫 사용의 편의성, 독립 리소스 셋 작성 편의성, DOM·Svelte·혼합·외부 패키지 일관성, 스타일 격리, 테마와 슬롯·팝업 동작, 로딩·정리·재적용 수명, 하위 호환성. `ui` 인식에 셋 이름이나 등록 여부만 쓰는 방안과 범용 함수 추가 가치도 검증한다. 지금은 실제 코드 변경이나 상세 구현 계획의 승인 없이 대안과 수락 기준을 제시한다.
