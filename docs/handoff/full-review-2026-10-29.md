# 전체 원문 감사 후 보완과 재검토 기록

> 이 문서는 해당 날짜·단계의 기록이다. 아래 미실행·후속·보류 표기를 현재의 승인 대기로 적용하지 않는다. 최신 계약·독립 검증 완료는 [U34–U35 진행표](verification-ledger.md), 새 채팅의 구현 시작과 U36 커밋 범위는 [현재 인수인계](implementation-start.md#새-채팅에서-시작할-때)를 따른다.

기준일: 2026-10-29. 이 문서는 보관 대화 전체와 회수 근거를 현재 계약에 대응시킨 후의 수정·검증 기록이다. 앞선 [9개 및 2개 보완 기록](semantic-review-2026-10-29.md)은 당시 범위/수량을 보존하며 현재 판정과 혼합하지 않는다. 구현·Schema 적합성·런타임 테스트 결과가 아니다.

아래 첫 재검토·검사 표는 그 단계의 기록이다. 이후 마지막 독립 재검토에서 URL 승인 누락 1건을 추가 발견했으며, 이 파일 끝의 마지막 보완·재평가가 현재 상태다.

## 범위와 근거 수준

사용자의 문서 수정·전체 재검토 반복 요청에 따라 작업했다. 기존 작업 트리와 원문을 보존하고 구현·설정·git add/commit/push는 범위에 넣지 않았다. 보관 transcript 27개의 1,530개 메시지를 6명이 각각 158/194/270/263/251/394개씩 파일 순서대로 전문 읽기한 결과를 [전체 대응표](source-contract-matrix.md)에 남겼다. 인용된 메시지만 다시 읽는 검사와 구별한다.

부모가 방 기록에서 직접 회수한 9개 부재 인용과 초기 적용 완료 승인은 로컬 `context-archive/recovered-evidence-2026-10-29.md`에 **검증 요약·명시 인용·ID**로 추가했다. 기존 33개 보관 파일과 transcript의 1,530개 메시지를 변경/증가시키지 않았다. 회수 요약을 원문 전체 export로 가장하지 않으며 공개 문서에는 필요한 계약만 보존한다. 전체 방의 미수록/삭제 메시지·첨부/도구 결과까지 완전하게 회수했다는 뜻은 아니다.

## 재검토와 실제 검사

**판정: 확인 가능한 승인 의미와 실제 미결의 구현 인수인계는 충분하다.** 수정 작성에 참여하지 않은 새 독립 검토자 3명이 전체 대응표·열린 과제·실제 공개 문서와 관련 제안/사용자 수락의 전후를 읽었다. 현재 문서끼리만 일치하는지 확인한 검사는 아니다. 각 검토자가 1,530개 전부를 다시 읽었다는 주장도 하지 않는다.

첫 독립 재검토에서 입력 변경 대기 중 자동 결합의 결과 재사용/갱신 중 표시와 Component 순환의 등록 검증 시점 누락을 추가 발견했다. E69/D48/Q22 및 E13/U11을 보완하고 관련 본문·이력·대응표·미결 범위를 다시 대조했다. 실패 후 보존의 인접 방 기록에는 독립 사용자 수락이 없다는 추가 확인도 보존하고 O16을 임의로 닫지 않았다. 재검토에서 세 검토자 모두 추가 필수 결함이 없고 다음 구현자가 승인 의미와 열린 과제를 구분할 수 있다고 판정했다. 실제로 찾은 결함을 고친 뒤 재평가한 결과이며 임의 횟수 제한이나 기준 축소로 종료하지 않았다.

## 판정의 적용 범위와 남은 한계

현재 공개 계약과 [열린 과제 O01–O16](open-contracts.md)로 다음 구현자가 core 타입/검증·명시 입력/상태·작은 Query/Action·렌더러 연결을 이어갈 수 있다. 알려진 승인 의미를 알아내기 위해 과거 채팅을 다시 추측할 필요는 없다. 상세 SDK·DTO·스키마가 이미 완성되었다는 뜻은 아니며 해당 기능을 구현으로 완료하기 전에 각 O행의 영향 상세와 fixture를 고정한다. 선택 차트는 core 기본 제공 의무와 구별한다.

HTTP 일부 최초 승인과 날짜 포맷의 세부 적용 문맥은 확인 수준을 공개해 뒀고, 실패 후 결합 데이터 정책도 직접 승인 없이 확정하지 않았다. 이 항목들은 명시된 확인/구체화 과제이며 일괄 core 착수 차단이나 새 사용자 승인 절차가 아니다. 실제로 기존 결정을 바꾸어야 하는 충돌이 생기면 해당 범위만 사용자 의도로 확인한다. 전체 방 원문의 완전성·미수록 내용·아직 없는 구현의 무결점이나 실행 테스트 통과를 보장하지 않는다.

## 마지막 독립 재검토의 URL 보완과 재평가

사용자의 마지막 재검토 요청으로 이전 판정을 전제하지 않고 22개 주제 매핑 전체, 현재 공개 문서·예시·인수 항목과 관련 실제 제안·수락·후속 변경을 다시 대조했다. 새 독립 검토자 3명이 T01–T09/T13–T14, T10–T12/T21–T22, T15–T20으로 나누어 확인했으며, 이 단계에서 1,530개 메시지 전부를 다시 전문 읽기했다고 주장하지 않는다. 회수 자료는 계속 검증 요약·명시 인용 수준으로 구별했다.

**확인한 결함(P2):** URL 값을 기본값과 같다는 이유로 자동 생략하지 않는 승인 경계가 공개 URL 규범과 인수 사례에서 빠져 있었다. 10/14의 `Sentinel_eca39f8c78248191888f401343f2f06e` 제안, `Sentinel_df3ca85a66cc8191a6c68d333a99352e`의 후속 정리와 사용자 `Sentinel_72f4f5f36bfc81919d39aa88144e0afd` 수락을 실제 보관 본문에서 확인했다. 앞선 항목별 응답의 “이해했어”만으로 승인을 추정한 것이 아니다.

기존 수정·재검토 반복 승인 범위에서 main §5.3, URL 상세, E46, D35, MIG07, T09, O11과 L12–L13에 복원했다. 모든 초기 기본값을 최초 연결 때 URL에 기록하라는 새 요구를 추가하지 않았다. key 부재의 baseline 복원, URL 복원 재push 금지, opt-in, 소유 key·해제/교체 정리 경계는 그대로 유지한다. 원문 보관 파일은 수정하지 않았다.

수정 후 같은 세 독립 검토자가 각 담당 범위와 변경 영향을 재평가하고 실제 원문에 비추어 아래 반례를 확인했다.

- baseline 10/14·현재 URL 10/13에서 날짜를 10/14로 바꾸어 기록할 때 key를 삭제하면 다음 날 새 baseline 10/15로 잘못 복원된다. 복원한 규범과 L12는 기본값 일치만을 이유로 한 삭제·생략을 금지한다.
- 처음부터 날짜 key가 없는 링크는 해당 실행의 baseline을 사용한다. L13과 본문은 이 경우 모든 초기값의 최초 기록이나 복원 재push를 요구하지 않는다.
- 폐기된 화면의 URL 쓰기 차단, 소유 key 정리, 서비스 상태 유지와 Query/Action·Component/View·선택 차트 계약의 구분도 유지된다.

이 반례 대조는 문서 의미의 검토이며 실제 Viewstem 런타임을 실행한 테스트가 아니다. 수정 후 세 검토자 모두 담당 범위의 추가 구체적 중대 결함을 찾지 못했다. **현재 판정: 확인 가능한 승인 의미와 명시된 실제 미결을 전달하는 core 착수용 인수인계로 충분하다.** 완전히 닫힌 구현 설계나 무결점 보장은 아니다. 이번 복원에 추가 사용자 결정은 필요하지 않다.

O01–O16은 계속 적용한다. 특히 nullable 연결 호환성의 과거 assistant-only 발췌와 HTTP 일부 세부는 최초 사용자 승인 근거가 부족하고, 날짜 포맷의 정확한 적용 문맥과 실패 후 결합 데이터 정책도 남아 있다. 이를 새로 확정하거나 옛 필드를 부활시키지 않았다. 등록 U01은 현 프로젝트 명확화로 구별하며, 이번 검토에서 해당 프로젝트 원문을 독립 재조회한 것은 아니다.
