# Viewstem 워크스페이스 성능 점검

## 1차 비교

이 절은 포트 컴파일 변경 뒤의 `bf85152`와 당시의 중간 후보를 비교한 기록이다.
Apple M2, macOS 15.8, Node 22.23.4와 Playwright
Chromium에서 같은 예제를 순차 실행했다. 전체 비교는 예제별 예열 1회와 측정
3회, Core 및 UI의 변경별 비교는 예열 2회와 측정 7회를 사용했다. 실행 명령과
구간 정의는 [벤치마크 안내](../../bench/README.md)에 있다.

| 대상 | 시나리오 | 범위 |
| --- | ---: | --- |
| Core | 26 | 등록과 참조, State와 Derived, 값 검증, CEL, URL, Grid, Action, HTTP, Query, View |
| DOM | 8 | 기본·커스텀 연결자, 슬롯과 키 유지, 이벤트, 해제, DOM·PostCSS 스타일 스코프 |
| Svelte | 6 | 어댑터 수명, 슬롯, 혼합 렌더링, 호스트 소스 교체 |
| UI | 76 | 66개 패밀리 마운트와 대형 선택기·테이블·폼·달력·메뉴 동작 |
| 문서 앱 | 123 | 영어 레슨 39개와 컴포넌트 페이지 66개, 한국어·모바일 예제, 검색·워크벤치·플레이그라운드 |

기준본과 수정본에서 239개 시나리오의 동작 검증을 통과했다. 독립 검토 후
DOM 키 유지, 브라우저 예외, 메뉴 열림, 정렬 순서, 필터 결과를 확인하도록
벤치를 보강하고 관련 14개를 두 빌드에서 다시 실행했다.

| 변경별 측정 | 기준 중앙값 | 수정 중앙값 |
| --- | ---: | ---: |
| Query Join 3,000 × 3,000행 | 49.7–60.0ms | 0.58–0.78ms |
| Type 100개 등록 및 순차 갱신 | 164.8–183.4ms | 11.4ms |
| State·Derived를 가진 반복 인스턴스 200개에서 공유 상태 3회 갱신 | 104.6–108.2ms | 27.3ms |
| NativeSelect 옵션 953개 마운트, Core 변경을 양쪽에 적용 | 56.2ms | 49.4ms |
| NativeSelect 옵션 953개에서 선택, Core 변경을 양쪽에 적용 | 55.7ms | 52.0ms |

- Join은 반대쪽 행을 키로 인덱싱한다. 복합 키의 타입 구분, null 처리, 중복
  매칭 순서와 오른쪽 필드 우선순위를 확인했다.
- Registry는 검증 한 번에 Type 목록을 한 번 만들고, 내부에서 깊게 동결한
  정의의 스키마 컴파일 결과를 재사용한다. 가변 입력 스키마는 호출 시점의
  값을 사용한다.
- Derived 계산을 같은 연결로 다시 묶을 때 의존 그래프를 순회하는 작업을
  생략한다. 연결 변경 시 순환 검사와 실패한 변경의 복구를 확인했다.
- UI는 관리 대상 속성을 한 번 모으고 목록이 바뀔 때 DOM에 반영한다. 입력
  속성이 빠지면 같은 노드에서 기존 속성을 제거한다.

시스템 작업이 겹친 구간에서는 문서 앱의 표본 편차가 컸다. 전체 비교에서
중앙값이 3ms와 20%를 모두 넘게 증가한 문서 사례 16개를 재측정했고, 모두
이 기준 안에 들었다. 수치는 로컬 DOM 및 렌더러 완료 시점, 고정된 모의 HTTP
데이터, 명시한 예제 규모를 기준으로 해석한다.

Core 1,216개, DOM 25개, Svelte 57개, UI 46개의 테스트를 통과했다. Core의
Chromium 및 배포 패키지 검증과 DOM·Svelte 패키지 소비자 검증도 통과했다.
문서 앱은 빌드, 타입 검사, HTML 327개와 링크 36,588개 검사를 통과했다.

## EGM 수정 반영 후 전체 검증

브랜치 분기점 `4cc2d04`를 Git archive로 내보낸 기준본과 `36a6c40`에
EGM 후속 수정이 적용된 후보를 비교했다. 두 빌드와 실행에 Node 22.23.4를
사용했다. [동일 fixture로 재현하는 실행 절차](../../bench/README.md#compare-a-revision-with-the-current-source)

벤치 10개 파일과 잠금 파일의 해시, 시나리오 ID와 작업량이 양쪽에서
일치했다. 기준 archive의 벤치 외 추적 파일 변경은 0개였다. 후보의 실행
시점 변경 해시는 `69c9a72b701d1a409d9364916edab929d8a53a715069713814fd11f2a4b534d0`,
공통 fixture 해시는 `064be3d6c38046b42c12a86b566f3f63bea43858944c5c753fa5d2e26deabae1`이다.

Core 41개, DOM 10개, Svelte 6개, UI 78개, 문서 앱 123개로 총 258개를
양쪽에서 한 번씩 실행했고 실패는 0건이었다. 이 검증은 작업량과 완료
조건의 일치를 확인한다. 처음 실행한 전체 3표본 비교는 Node 버전이 달라
시간 비교에서 제외했다.

- Svelte 어댑터는 Query 핸들이 전달된 경우 지연 응답의 `running`과
  최종 결과를 표시한다. State 쓰기로 외부 Query 게이트가 바뀌면 연결된
  View도 쓰기 중 갱신된다. 포트를 다시 연결하거나 수명이 끝나면 이전
  연결의 통지가 중단된다.
- 복합 Join 키는 요소별로 인덱싱한다. 긴 키가 여러 위치에 쓰이는 두 행도
  매칭된다. DataTable은 폼 초기화 뒤 다음 투영에서 제어값을 복원하며
  일반적인 무관 갱신에서는 표시 행을 유지한다.
- Query 알림 누락은 벤치 실패로 기록된다. Svelte 교체 사례는 새 값과
  수명, 스타일 스코프 사례는 실제 소유 표식을 검사한다.

Core 1,221개, DOM 25개, Svelte 58개, UI 48개와 벤치 실패 처리 테스트
2개가 통과했다. Core·DOM·Svelte의 소비자 검증과 문서 앱 빌드·타입 검사도
통과했다.

같은 빌드와 fixture로 주요 11개 사례를 예열 2회, 측정 7회씩 순차 실행했다.
작업 사이 시스템 부하가 낮아질 때까지 대기한 후 다음 실행을 시작했다.
아래 값은 각 측정의 중앙값이다.

| 사례 | 기준 | 후보 |
| --- | ---: | ---: |
| 무관 View 6개를 둔 State 쓰기 | 39.40ms | 0.61ms |
| 무관 State 구독 256개 | 36.55ms | 0.58ms |
| 정적 반복 1,000개와 분리된 Query 응답 6건 | 75.59ms | 4.94ms |
| 동일 값으로 공유 Query 소비자 500개 갱신 | 18.81ms | 0.12ms |
| 다른 View에 공유한 Query 게이트 전환 | 0.132ms | 0.126ms |
| Type 100개 등록·갱신 | 162.60ms | 10.82ms |
| State와 Derived를 둔 반복 인스턴스 200개 | 112.30ms | 27.84ms |
| Query Join 3,000 × 3,000행 | 50.45ms | 0.77ms |
| 변경 없는 옵션 1,000개와 Query 결과의 DOM 반영 | 14.20ms | 2.30ms |
| 무관한 DataTable 4개와 요약 응답의 DOM 반영 | 6.60ms | 2.00ms |
| NativeSelect 옵션 953개 중 선택 | 912.60ms | 48.80ms |

무관 View 발행은 6회에서 0회로 줄었고, DataTable 네 개에서 유지된
표시 행은 0개에서 400개로 늘었다. 시간은 로컬 모의 입력에서 해당
시나리오의 완료 지점까지 잰 값이다.
