# 2026-10-29 승인 계약 복원과 문서 검증

> 이 문서는 해당 날짜·단계의 기록이다. 아래 미실행·후속·보류 표기를 현재의 승인 대기로 적용하지 않는다. 최신 계약·독립 검증 완료는 [U34–U35 진행표](verification-ledger.md), 새 채팅의 구현 시작과 U36 커밋 범위는 [현재 인수인계](implementation-start.md#새-채팅에서-시작할-때)를 따른다.

상태: 아래 앞선 9개 복원 기록 이후 추가 재평가에서 Query 실패 의미 누락과 등록 ID 범위 모호성을 발견했다. 사용자 개선 요청에 따른 [두 항목 보완](#추가-재평가-후-두-항목-보완)을 별도로 기록한다. 어떤 검사도 런타임 구현·Schema 적합성·테스트 통과 보고는 아니다.

**이 문서는 앞선 두 단계의 당시 검사 기록이다.** 이후 전체 원문 감사·회수 근거 보완과 현재 이관 판정은 [전체 대응표](source-contract-matrix.md)와 [후속 수정·재검토 기록](full-review-2026-10-29.md)을 따른다. 아래의 ‘원문 부재/최초 승인 미확인’은 당시 조회 한계이며, 현재는 회수 요약/명시 인용으로 추가 확인한 항목과 구별한다.

## 목적과 작업 경계

최종 적대적 리뷰에서 통합 요약에 이미 승인된 의미가 누락되거나 좁아진 9건을 확인했다. 사용자의 개선 요청에 따라 현재 명세·결정/이관 기록·인수 백로그에 복원했다. 원문 보관함은 수정하지 않는다. 구현, git add/commit/push, 설정 변경은 이번 범위에 없다.

[이전 이관 검사](transfer-verification.md)는 2026-10-28 파일 묶음의 수량·형식·전달 일치 기록이다. 일부 누락이 당시 canonical 스냅샷에도 있으므로 그 원본과 같다는 사실이 의미적 완전성을 보장하지 않는다. 이번 작업은 실제 제안과 사용자 수락을 다시 대조한 의미 복원이다. [보충 근거 E43–E51](../history/evidence-index.md#2026-10-29-누락-복원의-보충-근거)은 신규 기능 승인이 아니다.

## 확정으로 격상하지 않은 것

- Join 전체 필드 문법·추가 변환 연산, 빈 Concat.with와 복사 깊이.
- Assert.message의 필수/생략·동적 평가·정확한 오류 DTO.
- refresh:false·확정된 View 기본값 상속을 새 사용 맵에 매핑하는 위치/표기, 제외 시 단계 결과와 복구 retry API·정책.
- StateStore 관찰의 현행 주소·changes 대상 필드·함수 시그니처·내부 관리 방법.
- URL의 수치 한계·정확한 제한 프로필·날짜 codec·새 어댑터 SDK.
- Query 콜백 변환을 넘는 새 DTO 전체·State/정의 export·CEL·Dart 직렬화.
- JSON Schema draft/프로필·literal escape·missing/null/undefined·CEL 구현체 적합성 등 기존 열린 계약.

원문 보관함은 읽을 수 있었으며 공개 문서에는 승인 의미와 근거 식별자만 복원했다. 전체 비공개 대화나 회사 정보를 옮기지 않는다. 새로 대조한 E43–E51과 원본 E01–E42를 구분한다.

기존 보존 부록이 인용하는 아래 9개 메시지의 본문은 현재 보관함에 없다. 이번 작업에서도 내용을 추정해 채우거나 새로 검증했다고 표시하지 않는다.

독립 검토자 3명이 Action/UI, 데이터/Query, Store/URL/인수인계로 나눠 실제 수정 파일·편집 직전 사본·승인 원문을 읽었다. 첫 재리뷰에서 URL의 실제 쓰기 직전 유효성 검사 누락을 추가로 찾아 같은 4번 항목에 복원하고 L09–L10을 추가했다. Query의 확정된 View 기본값 상속을 다시 미결처럼 읽을 수 있던 문구도 매핑 세부로 좁혔다. 재검토에서 세 담당 범위 모두 남은 차단 결함이 없다고 확인했다. 이는 전체 미수록 대화의 완전성 보장이나 런타임 검증이 아니다.

## 추가 재평가 후 두 항목 보완

재평가 보고 후 사용자의 개선 요청에 따라 다음 두 항목을 보완했다. 앞선 9개 복원이 잘못됐다는 뜻이나 과거 정적 검사로 의미적 완전성이 증명됐다는 뜻이 아니다.

| 항목 | 현재 계약·근거 수준 | 연결 |
|---|---|---|
| Query 실패 의미 | E52의 실제 제안·수락에 따른 기존 승인 복원. 필요한 source/단계 실패는 전체 실패·부분 성공값 금지·정상 빈 결과 성공·실패 source/단계 식별 정보 보존 | [Query 상세](../spec/02-query.md#query-실패의-확정-의미), D38, Q16–Q17 |
| 등록 식별 | U01의 이번 사용자 개선 요청에 따라 (kind, id)로 명확화. 같은 종류 중복 거절·다른 종류 같은 ID 허용; 코드형/선언형 Component와 Action은 각각 같은 종류 범위 사용; xxxRef는 기대 종류만 조회 | [공통 등록 계약과 예시](../VIEWSTEM-SPEC.md#41-정의와-인스턴스), D37, C03·C16–C17 |

오류 DTO·단계 위치 표현과 과거 성공 캐시 유지/표시 정책, SDK 함수명·인스턴스 주소 등 기존 미결을 추가 확정하지 않는다. Query 실패 위치를 남긴다는 이유로 모든 변환 단계에 필수 id를 요구하지 않는다. 등록 규칙에 버전 접두사나 새 참조 객체를 추가하지 않는다.

이 단계 당시에는 setResource 완료의 최초 승인이 확인되지 않았다. 이후 방 기록의 사용자 수락을 회수해 E61로 확인했고 현재는 [초기 적용의 승인 관찰 의미](../spec/09-preserved-contracts.md#초기-적용-완료의-확정-관찰-의미)를 보존한다. 새 SDK 이름/반환 시그니처와 실행 테스트 통과를 뜻하지 않는다. E52의 보관 원문과 U01의 현재 프로젝트 대화는 [근거 색인](../history/evidence-index.md#추가-재평가와-현재-프로젝트의-명확화-근거)에서 구별한다. 회수 근거는 원 transcript를 변경하지 않고 별도 파일에 요약·명시 인용으로 보존한다.

### 후속 보완의 실제 검증

독립 검토자 3명이 변경 직전 사본과 실제 수정본을 읽고 Query/Action 의미, 등록·참조·예시, 기존 Store/URL/수명 보존을 나눠 확인했다. E52의 실제 제안·수락과 현재 U01의 근거 구분, 미결 DTO/캐시/SDK 유지, setResource 완료의 승인 확인 상태를 재검토했으며 이번 변경 범위의 남은 구체 결함은 찾지 못했다. 이는 전체 설계의 무결점 보장이 아니다.

| 실제 실행한 후속 검사 | 최종 결과·범위 |
|---|---|
| 파일 inventory | Markdown 53개: 공개 20개·원문 보관 33개 |
| 상대 링크·앵커 | 상대 링크 390개·fragment 194개, 파일/heading/명시 anchor 오류 0 |

| 인수 목록 | 고유 ID 93개·중복 0. C03 보강, C16–C17·Q16–Q17 추가; 전부 설계 기대값·미실행 |
| 근거 접근성 | E52의 3개 ID는 기존 보관 원문에 존재. 부재 과거 근거는 앞선 9개 그대로이며 U01의 현재 프로젝트 근거 1개는 별도로 분류 |
