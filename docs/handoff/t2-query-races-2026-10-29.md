# T2 Query 지연 응답·취소 경합 실험

기준일: 2026-10-29. U17은 오래된 Query 응답·취소·화면 교체와 fresh 갱신 대기를 재현하는 **독립 실험**의 진행 승인이다. [실험 코드·명령](../../experiments/t2-query-races/README.md), [Node 22 결과](../../experiments/t2-query-races/results/latest.json), [Node 24 결과](../../experiments/t2-query-races/results/node24.json)를 남긴다. core 본 구현·CEL 패치·배포는 수행하지 않았다.

## 판단

현재 Query 계약은 이번 범위에서 작은 JS 스케줄러 프로토타입으로 구현 가능했다. 같은 논리 주소를 재사용하더라도 **소유 수명·입력/gate 세대·요청 종료 여부를 결과 반영 시점에 확인**하면 오래된 성공/실패가 현재 상태를 덮어쓰지 않았다. 입력 A→B→A처럼 값이 원래대로 돌아오는 경우에도 옛 실행을 새 실행으로 취급하지 않았다.

취소 신호는 전송기에 전달했지만 전송기가 이를 무시하도록 구성했다. 그 상태에서도 늦은 완료를 차단했다. 이는 실제 외부 작업의 중단·롤백 보장이 아니라 상태 반영의 보호다. timeout/폐기 뒤 외부 작업이 계속되는 동안 새 수명의 요청은 실행될 수 있다. 일반 입력 변경에서는 사용 인스턴스의 이전 active가 끝난 후 최신 pending 하나만 시작한다.

**추가 제품 선택이 필요한 계약 충돌은 이번 범위에서 발견하지 않았다.** 실제 core와 연결된 증거가 아니며 T2 전체 완료로 판단하지 않는다.

## 실행 결과와 범위

macOS arm64, Node 22.21.1/24.19.0에서 동일 소스를 실행했다. 외부 의존성·실제 네트워크·렌더러 없이 가짜 시계와 제어 가능한 전송 Promise를 사용했다.

|---|---|---|
| 대표 시간순 사례 | 36/36 통과 | 오래된 성공/실패, 입력/gate ABA, Promise 완료 뒤 반영 전 변경, 최신 pending, refresh 대기 결합, 같은 주소 교체, 취소, timeout, 실패/재시도 |
| 보호 장치 제거 대조군 | 4/4 탐지 | 세대·소유 수명·완료 표식 검사를 제거하거나 refresh를 기존 active에 결합하면 해당 assertion이 실패 |

보고서의 소스 해시는 package.json·harness·query-probe·scenarios·runner를 포함한다. 인수 ID 18개와 관련된 **일부 경로**를 실행했으며 해당 인수 ID 전체의 완료를 뜻하지 않는다. 단순 assertion 수를 제품 기능 수로 확대하지 않는다.

## 구체적으로 확인한 경계

1. **반영 직전 검사:** 응답 Promise가 이미 resolve됐어도 그 반응이 실행되기 전에 입력이나 소유 수명이 바뀌면 결과를 폐기해야 한다. 요청 시작 시에만 검사하는 것으로 충분하지 않다.
2. **fresh 대기 결합:** 기존 active 중 들어온 두 refresh는 다음 실행을 함께 기다린다. 그 다음 실행이 시작된 후 들어온 refresh는 다시 그 이후 실행을 기다린다. 도중 입력이 바뀌면 대기자는 최신 입력의 유효한 실행으로 이어진다.
3. **취소 범위:** Query 소유자 폐기는 관련 대기자를 CANCELLED로 끝내지만, 호출 한정 핸들의 취소는 다른 호출과 공유 Query를 폐기하지 않는다. gate 종료는 대기자를 EXECUTION_BLOCKED로 끝낸다.
4. **완료 표식:** timeout 뒤 늦은 성공뿐 아니라 실패도 무시해야 한다. 옛 실패가 새 실행의 running/error 상태를 바꾸거나 새 active를 지우지 못하게 한다.
5. **이전 성공 보존:** 새 실행 실패에도 data·dataInputs를 함께 보존한다. null·false·0·빈 문자열·빈 배열을 missing으로 취급하지 않는다. 입력 변경 시 stale, 새 실행 시작 시 error 해제, 새 성공 시 쌍의 교체를 확인했다.

제작 중 대표 34개 사례를 통과한 초기 프로토타입에 관찰 검사를 추가하자, 이전 성공 뒤 입력이 바뀌고 바로 다음 실행을 시작하는 경로에서 stale:true가 빠진 것을 발견했다. [수정 전 기록](../../experiments/t2-query-races/results/development-failure.json)의 36개 중 1개 실패는 이 실험 모델의 결함이다. 입력 변경 시 새 실행의 stale을 설정하고 상태만 바뀔 때 보존 data의 참조를 유지하도록 수정했다. 최종 36개 사례와 기존 보호 장치 대조군·반복을 모두 다시 실행했다. 기존 서비스나 아직 없는 core의 버그를 수정했다고 보고하지 않는다.

## 남은 검증

- T2의 실제 HTTP 계획·Login·secret/권한·응답 파싱, 실제 전송기의 timeout/협력 취소, URL의 실제 commit 직전 유효성.
- 복합 Query의 유효 snapshot 결합, 전체 source 실패와 부분 결과, 완료 시점 기준 polling 스케줄, 브라우저 실행.
- 등록·타입 검증·StateStore·실제 Action 호출 수명·renderer의 이전 결과 표시 및 교체와의 연결.
- T1의 CEL 패치와 전체 값 어댑터, T3의 SDK/renderer, T4의 선택 차트. 이번 실험으로 상태를 변경하지 않는다.

다음 T2 검증은 URL 비동기 쓰기의 **실제 반영 직전** 오래된 작업 차단으로 이어갈 수 있다. Query 결과 폐기와 달리 URL은 외부 변경이므로 완료 Promise만 무시하는 방식으로 검증을 대체하지 않는다. 이는 후속 제안이며 이번 실행 범위에 포함하지 않았다.

후속 U18에서 [URL 경합 실험](t2-url-races-2026-10-29.md)을 별도로 수행했다. 위 U17 결과와 범위를 소급 확대하지 않는다.

## U29 후속: 실제 HTTP 연결

[별도 연결 실험](t2-query-http-2026-10-30.md)에서 현재 스케줄러와 HTTP/Login 실행기를 실제 loopback HTTP로 연결했다. Node 22/24 각각 39/39·고의 결함 4/4를 확인했고 두 기존 구현은 변경하지 않았다. 위 U17 결과는 당시 단독 실험의 범위로 유지하며, 일반 Query DSL·복합 Query·실제 core/URL/renderer 연결은 여전히 포함하지 않는다.

## U30 후속 검증

[복합 Query·완료 기준 polling](t2-composite-polling-2026-10-30.md)을 연결하며 공유 스케줄러에 fresh 구분·정제 오류 위치/resource·owner 해제 hook을 추가했다. 기존 36개·고의 결함 4개·100 seed를 Node 22/24에서 재실행해 유지했다. 현재 결과 파일의 해시는 U30 회귀 소스이며 [수정 전 증거](../../experiments/t2-composite-query/archive/u30-development/README.md)와 구별한다. U17 단독 실험의 제한이 후속 독립 실험 전체의 미검증 상태를 뜻하지 않도록 위 U30 범위를 함께 읽는다.
