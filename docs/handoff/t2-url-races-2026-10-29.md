# T2 URL 지연 쓰기·복원 경합 실험

기준일: 2026-10-29. U18은 URL 비동기 쓰기의 실제 반영 직전 유효성 검증을 진행하라는 요청이다. [실험 코드·재현 명령](../../experiments/t2-url-races/README.md), [Node 22 결과](../../experiments/t2-url-races/archive/u18-before-boundaries/snapshot/experiments/t2-url-races/results/latest.json), [Node 24 결과](../../experiments/t2-url-races/archive/u18-before-boundaries/snapshot/experiments/t2-url-races/results/node24.json), [Chromium 결과](../../experiments/t2-url-races/archive/u18-before-boundaries/snapshot/experiments/t2-url-races/results/chromium.json)를 보존한다. core·renderer·실제 HTTP·CEL 패치 구현은 수행하지 않았다.

아래는 U18 당시 결과다. 최신 URL 교체·실패 경계는 [U32/U33 후속 기록](boundary-followup-2026-10-30.md)을 따른다.

## 판단

현재 URL 계약의 대표 경로를 독립 연결 모형과 실제 Chromium History API에서 실행할 수 있었다. 오래된 쓰기는 **실제 URL commit 직전** 차단했고, 유효한 쓰기는 그 시점의 최신 URL에 정확한 소유 key 변경분만 반영했다. 검사 이후 최종 변경까지 비동기 대기를 두지 않는 경계를 확인했다. Promise 완료 결과만 무시하거나 요청 시작 시에만 유효성을 검사하면 실제 주소가 오염되는 대조군도 탐지했다.

새 쓰기가 옛 쓰기를 무효화할 때 **아직 반영되지 않은 다른 key 변경분을 보존**해야 한다. x 쓰기가 대기 중일 때 y를 바꾸면 유효한 최신 작업에 x와 y 모두 남아야 한다. 이번 모형은 미반영 key 집합을 누적하고 현재 작업의 성공에서만 비웠다. 이는 구체 자료구조를 공개 SDK로 고정하는 결정이 아니라 기존 URL/State 의미를 보존한 구현 증거다.

이번 범위에서 새로운 제품 선택이 필요한 충돌은 발견하지 않았다. 실제 core에 연결한 결과나 T2 전체 완료는 아니다.

## 실제 실행

macOS arm64, Node 22.21.1/24.19.0, Playwright 1.62.1, Chromium 151.0.7922.34를 사용했다. lockfile의 Playwright를 `npm ci --ignore-scripts`로 설치했다. 별도 headless 브라우저의 임시 문서에서 실제 `history.pushState/replaceState`, `location.href`, `history.go`와 `popstate`를 관찰했다. 사용자의 기존 브라우저·실제 서비스 URL은 사용하지 않았고, 실행 후 임시 서버와 브라우저를 종료했다.

| 구분 | 결과 | 의미 |
|---|---|---|
| Node 대표 사례 | 두 버전 각각 36/36 | 통제 가능한 지연 쓰기로 URL·baseline·소유 key·제한·history 규칙 확인 |
| Chromium 대표 사례 | 36/36 | 같은 fixture의 실제 주소 변경, 뒤로/앞으로 복원, 오래된 commit 차단 |
| 잘못된 구현 대조군 | 세 환경 각각 6/6 탐지 | 검사 생략, 검사 시점 오류 2종, 옛 URL 덮기, 미반영 key 유실, 복원 시 무효화 누락 |
| 완료 순서 반복 | Node 각 100/100, Chromium 20/20 seed | seed당 18회 쓰기. Node 1,800회·Chromium 360회 요청의 완료 순서를 섞음 |
| 환경 대조 | 일치 | 정상 사례의 최종 URL·commit/작업 trace, 공통 seed 결과, 소스 7개 해시 일치 |
| 구문·브라우저 오류 | JS 5개 구문 검사 통과, pageerror 0 | 전체 브라우저/보안 검증과 구별 |

테스트의 대조군은 의도적으로 잘못 만든 모형이다. 기존 서비스나 외부 라이브러리에서 여섯 취약점을 발견했다는 뜻이 아니다. 임의의 모든 스케줄을 탐색하거나 처리량·실제 사용자 환경의 성능을 측정하지 않았다.

## 보존된 의미와 발견한 구현 실수

- 새 쓰기·URL 복원·연결 폐기·명시 교체 뒤 옛 작업이 실제 주소를 바꾸지 않았다. 비동기 준비 중 무효화도 최종 검사로 차단했다.
- 서로 다른 연결의 key와 URL path/hash를 보존했다. 같은 prefix의 다른 key와 기존 percent encoding도 유지했다. 소유 key 정리는 삭제 patch의 null과 실제 값 null의 JSON 문자열을 구별했다.
- 매 복원은 고정 baseline에서 시작했다. 잘못된 값·중복 key·부재는 baseline으로 돌아가고 missing을 null로 만들지 않았다. 실제 뒤로/앞으로 이동에서 복원 때문에 새 push가 생기지 않았다.
- URL 쓰기 실패와 출력 한도 초과는 유효한 State 값을 되돌리지 않았다. 출력은 일부 key만 적용하거나 자르지 않았으며, 바이트 한도를 최신 URL 병합 뒤에도 검사했다.
- 일반 dispose는 주소를 보존했다. 명시 교체 fixture는 이전 화면 소유 key만 replace로 정리한 뒤 새 초기값으로 연결했고, 서비스 연결과 다른 key를 유지했다.

첫 34개 사례 뒤 두 검사를 추가하자 다음 실수가 확인됐다. [수정 전 실행](../../experiments/t2-url-races/results/development-failure.json)은 36개 중 2개 실패다.

1. 이미 같은 값인 key를 지웠다가 뒤에 붙여 URL 순서만 바꾸고 불필요한 방문 기록을 만들었다. 같은 key/value는 기존 위치와 인코딩을 보존하도록 수정했다.
2. 변경되지 않은 push 설정 항목까지 묶음의 history 선택에 포함했다. 실제로 변경된 항목 및 아직 반영하지 않은 변경에 따라 push/replace를 선택하도록 수정했다.

둘 다 이번 독립 실험 코드에서 발견한 실수이며 기존 core 결함으로 보고하지 않는다. 수정 후 Node 두 버전과 실제 Chromium의 전체 사례·대조군·반복을 다시 실행해 위 결과를 얻었다.

## 남은 범위

- 실제 StateStore·전체 스키마·날짜 codec·reaction/Query 초기화 순서·renderer 교체와의 통합.
- View 교체 사전 검증·URL 정리 실패와 전체 적용 결과의 연결, 서비스 router, Firefox/WebKit·Dart.
- T2의 실제 HTTP Login+요청 timeout·협력 취소·secret/권한·응답 파싱, 복합 Query 결합과 polling 타이밍.
- T1의 CEL 패치·값 어댑터, T3 최소 SDK 타입/renderer, T4 선택 차트는 별도다.

다음 독립 검증의 우선순위는 HTTP 실행 경계다. URL 경합과 Query 경합이 통과했다는 이유로 실제 전송·비밀값 처리까지 검증됐다고 표시하지 않는다.

## 확인한 API 문서

브라우저 효과는 [History.pushState](https://developer.mozilla.org/en-US/docs/Web/API/History/pushState), [History.replaceState](https://developer.mozilla.org/en-US/docs/Web/API/History/replaceState)를 기준으로 직접 관찰했다. 브라우저 실행에는 [Playwright BrowserType](https://playwright.dev/docs/api/class-browsertype)을 사용했다.
