# 리소스 셋과 브라우저 렌더링 결정 이력

2026-11-16 이관 기록. [확정 설계](../spec/12-resource-sets-browser.md)와 [구현 인계](../handoff/resource-sets-browser-2026-11-16.md)를 함께 읽는다.

## 아키텍처 선택

| 비교한 방향 | 장점과 비용 | 판단 |
|---|---|---|
| Svelte 주도 구조(아키텍처 A) | 기존 keyed each와 snippet을 활용하기 쉽다. DOM 전용 앱에는 별도 바닐라 순회가 필요하며, 두 순회 사이에 identity·순서·슬롯의 의미 중복과 DOM slot bridge가 남는다. | 전체 구조의 기반으로 선택하지 않았다. |
| 공통 브라우저 기반과 공개 연결자(아키텍처 B) | Viewstem 공통 identity·slot·순서를 한곳에서 조정하고 각 구현의 책임을 분리할 수 있다. 실제 slot 소유권, 독립 마운트의 context, props 전달과 cleanup에 설계·검증 비용이 든다. | 사용자가 장기 구조로 선택했다. 성능 우위는 측정하지 않았다. |
| 전체 렌더러 사이의 bridge | 독립된 View를 별도 영역에 붙이는 용도는 검토할 수 있다. 일반 자식 조합에 쓰면 전체 View 중첩, 중복 순회, 이벤트·identity·정리 경합이 생긴다. | 일반 혼합 트리의 기반에서 제외했다. |

패키지 구성에서는 별도의 선택지 A를 채택했다. 공통 브라우저 기반과 바닐라 DOM 연결자를 `@viewstem/dom` 한 패키지에 두고 내부 역할을 나눈다. 아키텍처 B와 패키지 구성 A는 서로 다른 선택이다. 기존 `createRendererHost`의 View 단위 수명·완료·진단을 재사용하고, 공통 노드 조정은 필요한 범위부터 설계한다. 현재 코드를 전면 재작성하거나 거대한 범용 프레임워크 엔진을 만드는 방향은 채택하지 않았다.

## 선택과 교정

| 먼저 논의한 방향 | 최신 결정과 배경 |
|---|---|
| 컴포넌트 위주 묶음 또는 회사를 위한 프레임워크 계층 | Query·Action까지 담는 리소스 셋이 제품 경계다. 서비스가 Viewstem을 직접 사용하고 Patchview를 프리셋으로 가져온다. 외부 작성자와 기본 `ui`도 같은 공개 도구와 계약을 사용한다. |
| D144의 `@viewstem/ui`가 기본 카탈로그와 브라우저 JSON 렌더링을 함께 제공하는 구조 | 기본 카탈로그는 계속 DOM 리소스다. 공통 브라우저 기반과 DOM 연결자는 장기 구조에서 `@viewstem/dom`으로 분리한다. 새 패키지 구성을 구현하기 전에는 현재 호스트 API를 참고한다. |
| EGM의 기본 권고는 초기 조립 때만 검증·등록하고 새 View에 새 구성을 쓰는 방식 | 사용자가 실행 중 리소스 셋 추가를 선택했다. 준비 실패 시 원자성, 기존 View에 대한 등록 비가시성, 새 View의 최신 설정 적용이라는 기대를 유지한다. 열린 View에는 서비스가 대상을 지정해 새 설정을 적용할 수 있어야 한다. |
| 여러 저장소를 논의하고 한때 승인 | 이후 사용자가 첫 버전 범위를 실행 환경당 하나로 좁혔다. 향후 분리를 고려해 소유·접근 경계를 남긴다. 실제 분리 비용은 아직 알 수 없다. |
| 렌더러나 구현에만 중복·교체 규칙을 두거나 같은 계약의 여러 구현을 렌더러별로 고른다는 해석 | 사용자 교정에 따라 모든 리소스의 공통 계약이다. DOM Button 자체가 중복 등록되는 경우도 포함한다. 명시적 교체 경로의 필요성은 확정됐고, 계약과 binding identity 및 병렬 구현 선택 방식은 보류됐다. |
| 적용 실패면 언제나 이전 화면 전체를 복원한다는 단순화 | 대상 View의 검증·준비 실패는 기존 설정을 보존한다. 실제 mount·render 중 발생한 DOM·포커스·로컬 상태 변화의 완전 복구는 미확정이다. 이미 성공한 별도 등록, 다른 View, 외부 API 효과의 범위도 구분한다. |
| EGM 시점의 `dom` 패키지 분리 및 정확한 이름 미정 | `@viewstem/dom`의 역할과 이름은 사용자 선택으로 확정됐다. 구체 public API, entrypoint와 배포 의존성은 추후 결정한다. |

## 추가 적용의 View 수명 결정

EGM 후속 논의에서 사용자는 열린 View에 셋을 추가 적용할 때 기존 View 수명·State와 기존 정의 및 구현을 쓰는 인스턴스를 보존하는 안에 동의했다. 셋을 추가해 PlantMap을 참조할 수 있게 하는 것만으로 편집 중인 폼이 초기화될 이유가 없다. 현행 `replace()`는 같은 View의 내부 수명을 새로 시작하므로 이 동작을 추가 적용의 의미로 채택하지 않았다. 기존 연결의 변경이 필요한 후보는 준비 단계에서 거절하며, 명시적 교체의 수명 정책은 후속 논의에 남겼다. [추가 적용 계약](../spec/12-resource-sets-browser.md#공통-저장소와-view-적용) · [현행 호스트 계약](../spec/07-host-integration.md#최소-sdk와-적용-완료)

사용자는 이어 View 설정을 한 번 확정하고 렌더 완료와 실패는 표시 연결별로 관찰하기로 했다. 같은 View를 두 곳에 표시할 때 두 연결이 같은 리소스 구성을 사용하면서 각자의 속도로 렌더할 수 있고, 한쪽의 실패는 그 연결에서 처리할 수 있다. [View 적용 계약](../spec/12-resource-sets-browser.md#공통-저장소와-view-적용)

## 컴포넌트 구현 누락의 실패 단계 결정

사용자는 현재 표시하는 데 필요한 구현이 View 설정 후보에 빠져 있으면 준비 단계에서 거절하기로 했다. 이 경계는 준비 시점에 발견한 구성 오류가 열린 View의 설정으로 확정되는 일을 막는다. 적용 후 조건이 바뀌어 처음 필요한 구현이 없거나 한 표시 연결에서만 렌더할 수 없는 경우는 해당 연결의 렌더 실패로 관찰한다. [실패 경계 계약](../spec/12-resource-sets-browser.md#실패-경계)

## Runtime별 저장소 범위 결정

사용자는 앞서 말한 실행 환경의 기본 단위를 Runtime으로 구체화했다. Runtime 하나의 View들은 기본 저장소 하나를 쓰고, 독립 생성한 Runtime끼리는 같은 프로세스에 있어도 각자의 저장소를 사용한다. 서비스가 같은 저장소를 여러 Runtime에 명시적으로 주입하면 공유한다. 이 범위는 별도로 조립한 호스트의 리소스 ID 충돌을 피하면서 현행 Registry 주입 경로의 공유 의미를 이어간다. [저장소와 View 적용 계약](../spec/12-resource-sets-browser.md#공통-저장소와-view-적용) · [현행 Runtime 조립](../spec/07-host-integration.md#최소-sdk와-적용-완료)

## 셋 등록과 resolver의 게시 경합 결정

사용자는 게시 직전에 최신 저장소 기준으로 후보를 다시 검증하기로 했다. 셋 등록과 resolver 중 어느 쪽이 먼저 시작했는지와 관계없이, 같은 `(kind, id)`에 다른 정의가 충돌하면 먼저 게시된 정의를 유지하고 충돌한 후보를 원자적으로 거절한다. 서로 충돌하지 않는 후보는 모두 반영해 준비 중 다른 요청이 성공했다는 이유만으로 변경이 유실되는 일을 막는다. [셋 등록 계약](../spec/12-resource-sets-browser.md#셋-식별과-등록)

## 부모 슬롯 교체와 자식 수명 결정

사용자는 같은 슬롯 안에서 순서만 바꿀 때 같은 수명의 자식 렌더 인스턴스를 유지하기로 했다. 부모가 슬롯을 교체하면 기존 렌더 인스턴스를 한 번 정리하고 새 슬롯에 다시 마운트한다. Viewstem 노드 수명이 같으면 core State는 유지한다. 이 규칙은 반복 항목의 일반적인 재정렬에서 인스턴스를 보존하고, 마운트 대상이 바뀔 때는 DOM과 Svelte 연결자가 같은 정리·마운트 절차를 따르게 한다. [혼합 트리 소유권](../spec/12-resource-sets-browser.md#혼합-트리의-소유권)

## 표시 연결에서 보낸 이벤트의 유효성 결정

사용자는 Action 시작 시점에 이벤트를 보낸 표시 연결과 렌더 인스턴스가 유효하고, 현재 노드 수명과 구현 연결이 일치하는 이벤트만 처리하기로 했다. 렌더가 늦은 연결에서도 유효한 인스턴스는 입력을 받을 수 있다. 슬롯 교체로 정리된 인스턴스의 콜백은 같은 Viewstem 노드가 살아 있어도 새 Action을 시작할 수 없다. [혼합 트리와 이벤트 계약](../spec/12-resource-sets-browser.md#혼합-트리의-소유권)

## Action의 필수 호스트 기능 확인 시점 결정

사용자는 호스트 기능을 공급하지 않은 환경에서도 셋을 등록하고, Action 시작 직전에 그 Action의 필수 기능을 확인하기로 했다. 누락 시 실행 전에 오류를 반환한다. 이를 통해 router가 없는 서버도 같은 셋의 일반 Action을 사용할 수 있고, routing이 필요한 Action은 본문을 실행하기 전에 누락을 발견할 수 있다. [호스트 기능 계약](../spec/12-resource-sets-browser.md#headless-실행과-호스트-기능)

## 진행 중인 Query와 Action의 리소스 구성 결정

사용자는 이미 실행 중인 Query와 Action이 시작 시점의 정의와 구현으로 계속 실행되고, 추가 적용 뒤 시작하는 새 독립 실행부터 적용된 구성을 쓰도록 결정했다. 이 규칙은 UI 셋을 추가하는 동안 진행 중인 저장 요청이 끊기거나 다시 전송되는 일을 막는다. [View 추가 적용 계약](../spec/12-resource-sets-browser.md#공통-저장소와-view-적용)

## 명시적 리소스 교체와 View 수명 결정

사용자는 저장소에 게시한 교체를 새 View부터 적용하고, 열린 View는 서비스가 대상으로 삼아 명시적으로 적용할 때까지 기존 구성을 쓰기로 했다. 열린 View가 교체를 받아들이면 `replace()`처럼 내부 수명을 새로 시작하며 서비스 소유 State를 보존한다. 이 규칙은 교체로 달라지는 정의와 구현에 구 인스턴스를 부분 이행하는 부담을 줄이고, 기존 View의 편집 수명을 끝낼 시점을 서비스가 정하게 한다. [View 적용 계약](../spec/12-resource-sets-browser.md#공통-저장소와-view-적용) · [현행 호스트 계약](../spec/07-host-integration.md#최소-sdk와-적용-완료)

## 리소스 설정과 View 정의의 일괄 적용 결정

사용자는 리소스 설정과 View 정의를 한 요청으로 검증하고, 성공하면 둘을 함께 확정하고, 검증에 실패하면 기존 설정과 정의를 모두 유지하기로 했다. PlantMap 교체로 필수 입력이 바뀌는 경우 해당 리소스 설정과 새 입력을 쓰는 View 정의를 함께 검증할 수 있다. [View 적용 계약](../spec/12-resource-sets-browser.md#공통-저장소와-view-적용) · [실패 경계](../spec/12-resource-sets-browser.md#실패-경계)

## 셋과 연결자 실행 코드의 신뢰 범위 결정

사용자는 서비스가 신뢰해 직접 가져온 셋·연결자 코드만 실행하기로 했다. View JSON의 코드형 리소스 참조는 이미 등록된 구현만 사용하며, 미등록 구현은 오류로 처리한다. 서비스가 실행 코드와 실제 호스트 기능을 선택하는 책임을 갖는다. [실행 코드와 호스트 기능 계약](../spec/12-resource-sets-browser.md#headless-실행과-호스트-기능)

## 표시 연결 안에서 렌더 실패의 영향 범위 결정

사용자는 실패한 컴포넌트를 특정할 수 있을 때 그 컴포넌트와 해당 슬롯에 의존하는 자식만 영향받고, 독립적인 컴포넌트는 계속 렌더링하도록 결정했다. 해당 표시 연결의 렌더 완료 대기에는 실패를 보고한다. 예를 들어 PlantMap을 마운트할 수 없어도 같은 화면의 독립적인 검색 폼은 사용할 수 있다. [실패 경계 계약](../spec/12-resource-sets-browser.md#실패-경계)

## 기본 UI의 등록 경로 결정

사용자는 기존 소비자가 없다는 전제에서 `@viewstem/ui`를 일반 리소스 셋과 같은 방식으로 등록하기로 했다. 서비스가 직접 등록하거나, Patchview처럼 기본 UI를 의존 셋으로 선언한 다른 셋을 등록할 때 함께 등록한다. 같은 공개 등록 계약을 쓰므로 의존성 재사용과 충돌 검증도 다른 리소스 셋과 같다. [패키지 역할과 기본 UI 등록](../spec/12-resource-sets-browser.md#제품과-패키지-역할)

## 코드형 컴포넌트 ID당 구현 수 결정

사용자는 첫 버전에서 같은 저장소의 코드형 컴포넌트 ID 하나에 구현 하나만 연결하기로 했다. DOM과 Svelte 구현을 함께 제공할 때 각각의 컴포넌트 ID를 등록한다. 이 규칙은 한 View에서 두 구현을 사용할 때 각 노드의 리소스 참조로 구현을 결정하게 한다. 정의의 중복은 기존 `(kind, id)` 기준을 따른다. [셋 식별과 등록](../spec/12-resource-sets-browser.md#셋-식별과-등록) · [기존 정의 식별](../VIEWSTEM-SPEC.md#41-정의와-인스턴스)

## 공개 확장의 독립 소비자 수락 기준 결정

사용자는 독립 소비자가 공개 API만 사용해 셋과 연결자를 만들고 공식 연결자와 한 View에 섞는 사례를 수락 기준으로 채택했다. 공식 패키지 내부 경로에 기대지 않는 외부 확장이 가능한지 확인하기 위한 결정이다. [후속 수락 시나리오](../handoff/resource-sets-browser-2026-11-16.md#후속-수락-시나리오)

## 코드 Action 함수의 동일 ID 교체 결정

구현 준비도 재리뷰에서 D154의 구현 변경 시 새 ID 규칙과 상세 계획의 동일 ID 교체가 충돌했다. 사용자는 입력·출력·필수 호스트 기능이 같을 때 명시적 함수 교체를 허용하기로 했다. 이 조건에서 기존 `actionRef`를 사용해 수정본을 배포할 수 있다. 계약이 달라질 때는 새 ID로 등록한다. 교체 게시 후 진행 중 호출과 명시 적용 전 열린 View는 기존 함수를 사용하고, 새 View와 교체를 받아들인 View에는 새 함수가 적용된다. [보완된 D154](../spec/04-action.md#코드-action-등록과-갱신)

## 같은 적용에서 새 투영으로 바뀔 때의 렌더 대기 결정

사용자는 한 View 적용에서 아직 렌더 중인 화면을 더 최신 화면이 대체하면, 미완료 대기는 최신 화면의 결과를 따르기로 했다. 대체된 화면의 늦은 오류는 무시하고 이미 끝난 대기의 결과는 유지한다. 예를 들어 검색 결과가 아직 그리는 중인 로딩 표시를 대체하면 검색 결과 렌더를 기다린다. 로딩 표시가 먼저 그려져 대기가 끝났다면 그 결과가 유지된다. [View 적용과 표시 완료 계약](../spec/12-resource-sets-browser.md#공통-저장소와-view-적용)

## mount 준비와 렌더 완료의 분리 결정

사용자는 `mount().ready`에서 View 준비와 표시 연결의 성립을 확인하고, 실제 렌더 결과는 `whenRendered()`로 확인하기로 했다. 이 규칙은 첫 렌더에서 일부 컴포넌트가 실패해도 앱이 View를 받아 정상 컴포넌트를 제어할 수 있게 한다. [View 적용과 표시 완료 계약](../spec/12-resource-sets-browser.md#공통-저장소와-view-적용)

## 부모가 제공하지 않은 슬롯의 렌더 완료 결정

사용자는 부모가 렌더를 마쳤을 때 제공하지 않은 슬롯의 자식은 이번 표시에서 제외하고, 나머지 렌더 결과를 기준으로 대기를 완료하기로 했다. 접힌 패널은 닫힌 모습으로 렌더를 완료하고, 펼쳐져 슬롯을 제공하면 그때 자식을 마운트한다. [혼합 트리의 소유권](../spec/12-resource-sets-browser.md#혼합-트리의-소유권)

## View 준비 콜백의 Action 호출 결정

사용자는 View 설정 검증 함수가 그 자리에서 요청한 Action을 본문 실행 전에 거절하기로 했다. 기존 화면에서 사용자가 클릭해 시작한 Action은 확정된 설정으로 계속 처리한다. 이 규칙은 새 설정이 검증에 실패하더라도 검증 콜백에서 서버 저장 같은 외부 효과가 미리 실행되는 일을 막는다. [View 설정 적용 계약](../spec/12-resource-sets-browser.md#공통-저장소와-view-적용)

## 필수 입력 대기 중 렌더 인스턴스의 수명 결정

사용자는 이미 표시된 같은 노드의 필수 입력이 잠시 대기 상태가 되더라도 렌더 인스턴스를 유지하기로 했다. 대기 상태를 표시하고 해당 노드에서 새 Action을 시작하는 이벤트를 거절한다. 새 입력이 준비되면 차트의 내부 선택값 같은 로컬 상태를 유지한 채 화면을 갱신할 수 있다. [혼합 트리의 소유권](../spec/12-resource-sets-browser.md#혼합-트리의-소유권)

## 이전 호스트 API 작업과 EGM 리뷰

2026-11-13 11:59:40 KST에 시작한 이전 인터페이스 개선의 첫 목표는 API 개발자 사용성에 대한 EGM 리뷰였다. 당시 `codex/viewstem-host-api` 작업이 [PR #3](https://github.com/miinhlym/viewstem/pull/3)으로 이어졌다. 구현 계획과 배경은 [호스트 API 계획](../designs/viewstem-host-api-implementation-2026-11-13.md), 이관 작업의 실제 기반과 소스 확인 결과는 [구현 인계](../handoff/resource-sets-browser-2026-11-16.md#이관-기준점)에서 확인한다. 당시 사용자는 PR의 최종 검토·머지를 별도로 진행하기로 했다. PR 범위에는 새 `dom` 패키지와 `ui` 리소스 셋 분리가 포함되지 않았다.

리소스 셋과 혼합 렌더링의 별도 EGM 리뷰는 2026-11-13 19:32~19:38 KST에 읽기 전용으로 수행됐다. 당시 main `3819bdcd08882b0ea2b4c1a59f835e1b97793a82`, API 작업트리 `409dd6f426065d453c338179a3abaa3383deda1f`를 비교했다. 별도 URL·State 회귀는 그 리뷰 범위 밖이었다. 리뷰 당시의 코드 무변경 표기는 해당 리뷰 실행의 기록이다.

- Stage 5는 zoom-out과 inventive-catalyst, Stage 6은 설계 입력만 대상으로 한 comprehension, Stage 7은 design·structural·style, Stage 8은 통합 zoom-out이었다. 상세 구현 계획이 없어서 Stage 9 구현 준비도 검토는 수행하지 않았다.
- 공통 View 수명 호스트 재사용과 제한된 브라우저 노드 조정은 EGM의 권고다. 혼합 slot·focus·repeat·cleanup과 셋 원자성은 실행 검증 과제다. 리뷰어가 사용한 blocker는 상세 명세의 준비 조건에 관한 판단이며 현재 코드에서 발견된 혼합 렌더링 회귀를 의미하지 않는다.
- 명시적 identity·버전·출처 또는 내용으로 동일 셋을 판정하고 순환 경로를 진단하자는 것은 EGM의 구현 제안이다. 재진입·동시 등록으로 이미 게시된 상태를 덮지 않는지, 실행 코드의 신뢰 경계와 core가 어떤 구현 정보를 보유할지도 EGM에서 확인 과제로 제시했다. 제안된 알고리즘이나 자료구조는 채택 상태가 아니다.
