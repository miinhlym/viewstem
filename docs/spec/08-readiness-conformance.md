# 구현 준비 · 열린 상세 · 적합성

기준일: 2026-10-28 · Viewstem v1 설계 계약

[명세 시작점](../VIEWSTEM-SPEC.md) · 이 문서는 최종 명세의 주제별 상세다. **확정**과 **구체화 필요/구현 제안/이전 승인 이관**을 구분해 읽는다. JSON은 계약 설명이며 실행 검증 완료를 뜻하지 않는다.

## 11 현재 설계가 어디까지 되었는가

### 끝낸 것을 다시 질문하지 않을 영역

- 서비스 중심 1차 목표와 에이전트 2차 목표가 같은 모델을 사용한다는 방향.

- 공통 계약 / 언어별 코어 / 프레임워크 렌더러 / 서비스·에이전트 연결의 구분.

- 독립 리소스 7종과 참조/인라인 지원, Component 재사용과 StateStore 소유 범위, 공통 kind·id·선택적 name·spec, 내부 평탄화, schema/typeRef 경계와 xxxRef 명명.

- 통합 Query sources/transform과 CRUD 정의, 명시 Action 실행, 순차·실패 중단·입력 스냅샷, SetState·RefreshQuery·If·Assert, 선언형/코드형 공통 output 계약.

- 화면 상태·구성·공용 정의 변경과 저장의 구분, 코어 소유 변경의 일괄 적용.

- 원본 자동 추종 배제, 명시적 주입/업데이트.

- Component/View 단일 render 루트, slots 전용 전달과 작성자 문맥, 공개 events와 on, when·repeat·Grid 배치, 코드형 Component/Action의 공통 사용과 수명.

### 구현 전에 정리할 것

U13에서 O01–O16 전부를 대조해 기술 계약을 구체화했다. 아래는 주로 구현·검증 경로이며, [Q1–Q3](../handoff/open-contracts.md#중요한-논의-사항)는 U14에서 추천안으로 확정했고 실제 기술 검증은 T1–T4를 따른다. U35까지의 독립 검증 완료와 U36의 [새 채팅 구현 인계](../handoff/implementation-start.md#새-채팅에서-시작할-때)를 현재 기준으로 적용한다.

1. **core의 계약과 적합성 구현**

   - 리소스·Port·State·노드·단계의 타입/JSON Schema를 작성하고 아래 성공·실패 사례를 테스트로 옮긴다. 등록 식별은 (kind, id), 종류 간 같은 ID 허용·같은 종류 중복 거절로 명확히 했다. Query 실패 source/단계 식별 정보도 확정 의미다. 스키마 프로필·공통 오류는 U13을 따르고 실제 적합성을 검증한다. [U01, E52]

   - 1차 core는 실행/상태/검증 엔진이다. Button·Toast·차트·업무 리소스를 자동 등록하지 않는다. 선택 UI 모듈이 공개 계약과 구현을 제공하고 서비스가 명시 등록한다. 기존 차트 요구는 선택 모듈에 이관한다.

2. **서버 요청과 인증정보 경계**

   - U13의 HttpExecutionPlan·executeRequest·secret resolver 계약을 구현 검증한다. 저장 원본 재조회나 미저장 Query의 사전 저장은 필수가 아니다. 비밀값 선언·참조는 secrets/@path로 확정했으며, 현재 DTO/API의 독립 HTTP/URL 검증은 T2에서 수행했고 실제 core·서비스 어댑터 통합은 구현 단계에서 이어간다.

   - Query와 Action의 요청 실행에 같은 인증 주입·대상 API 권한 경계를 적용할 수 있도록 통합한다. 전용 인증 플랫폼이나 리소스별 서비스 업무 로직을 새로 요구하지 않는다.

3. **값 표현과 CEL의 구현 적합성**

   - U13의 동적 값 영역·재귀/escape·읽기 snapshot·명시 제거를 구현한다. 날짜 표현·업무 시간대·codec은 U14를 따르고 CEL/Dart 어댑터의 실제 적합성은 T1에서 검증한다. U02–U12의 값 수용·검증·비교 계약과 일반 path/call literal·동적 영역 @@ escape의 기본 의미는 확정이며 [값 상세](10-value-contracts.md)를 따른다. JSON Schema와 schema/typeRef 택일은 다시 선택할 의제가 아니다.

   - 기존 nullable/missing·숫자·날짜·Set/Map 정책을 Type·CEL·JS/Dart 계약에 이관한다([이전 승인 이관](09-preserved-contracts.md)). Query 서비스 콜백 직전의 재귀 Set→배열·Map→쌍 배열 변환과 라이브러리 책임은 이미 확정이다. 나머지 직렬화, 새 변경 프로토콜의 null/삭제 의미 등 실제 충돌 지점만 고정한다. [E47]

   - CEL 구현체·허용 순수 함수 카탈로그·실행 비용 제한을 검증한다. 언어 선택이나 spec.expression 이름을 다시 열지 않는다.

4. **수명과 변경을 보여주는 실행 테스트**

   - 기존 폴링/대기열/오류/파생 계산/reaction 결정을 새 모델에 옮긴다. 동일 Store·대상 reaction 중복 거절과 일반 RefreshQuery의 refresh:false 존중은 확정 의미이며, 등록/설정 위치·제외 오류·복구 retry는 U13에 따라 구현한다. [E44, E50]

   - 부분 변경/전체 재주입·반복 키·동일 노드 when/repeat 순서·진행 중 실행 폐기·늦은 응답 차단을 테스트한다. 취소 조건은 실제 호출 연결 제거와 소유자 폐기 모두 포함한다. 기존 소유권과 취소 방향은 유지한다. [E43]

   - 부분 변경 상태 보존과 전체 재주입 이행을 같은 문제로 처리하지 않는다.

5. **확장과 렌더러의 최소 SDK**

   - 코드 Component/Action 공개 계약과 구현 등록, 포트 핸들·취소 신호·오류 전달을 연결한다. 등록은 정의 준비이고 사용은 인스턴스 생성이라는 기존 분리를 따른다. StateStore는 라이브러리 생성 객체를 주입하며 임의 외부 Store는 별도 확장이다. 승인된 관찰/URL 의미를 U13의 주소·SDK에 맞춰 검증한다. [E45, E46, E51]

   - 예전 의사 코드에서 API를 추정하지 않고 U13의 최소 SDK 표를 따른다. 임의 새 리소스 kind나 모든 리소스의 코드형 구현을 1차 확장으로 추가하지 않는다.

### 코드 착수 기준

큰 설계는 core 구현을 시작할 만큼 구체화됐다. 남은 상세는 대표 사례를 타입과 테스트로 옮기는 과정에서 해결한다. 사용자에게 같은 결정을 다시 묻거나 작은 필드마다 승인을 요구하지 않는다. U12의 [세부 판단 위임 기준](../handoff/open-contracts.md#세부-판단의-위임과-논의-기준)을 적용하며, 현재 실행 순서는 [새 채팅 시작 절차](../handoff/implementation-start.md#새-채팅에서-시작할-때)를 따른다. 이 문서 정리는 코드 구현·저장소 생성·npm 발행을 수행했다는 뜻이 아니다.

**구현 제안:** 공통 타입/검증 → State/표현 평가 → Query 실행 → Action/코드 확장 → 렌더러 연결 순으로 작은 실행 경로를 만든다. 최초 코어 검증에서 서버 중계는 주입 인터페이스로 분리할 수 있다. 모든 미래 플러그인·Theme·Flutter까지 정할 필요는 없다. 구체화 중 공개 계약을 바꾸는 실제 충돌이 발견되면 그 범위만 의제로 올린다.

## 12 구현 전 적합성 시나리오

| 사례 | 기대 결과 |
|---|---|
| 같은 Component를 A/B 두 번 사용 | 로컬 상태는 분리, 공유 날짜만 함께 반영 |
| Component 정의를 등록만 함 | Query 실행 없음 |
| 단일 Query를 참조/인라인으로 교체 | 같은 입력·검증·실행 의미 |
| 복합 Query가 두 결과를 join | 단일 Query와 같은 소비 인터페이스로 최종 결과 제공 |
| 날짜 변경 중 이전 요청이 늦게 완료 | 현재 입력 결과처럼 오래된 값을 덮어쓰지 않음 |
| 폼 저장 직후 사용자가 입력 편집 | 이미 호출한 Action 입력은 변하지 않음 |
| 저장 성공 후 목록 갱신 실패 | 저장을 취소/실패로 오인하지 않음 |
| 유효하지 않은 구성 변경 묶음 | 코어 상태·구성에 부분 적용 없음 |
| 구성 반영 후 Query 실패 | 구성 자동 취소가 아니라 조회 오류 |
| 공용 원본을 서비스 DB에서 수정 | 실행 중 화면 자동 변경 없음 |
| A만 에이전트가 수정 | B 및 공용 원본은 명시 요청 없이는 변경 없음 |
| 목록 순서 변경 | 안정적인 항목 키를 따라 코어 상태 유지 |
| 같은 ID 제거 후 재추가 | 새 수명, 오래된 실행 결과가 새 대상에 섞이지 않도록 검증 |
| 권한 없는 API·장비 요청 | UI 노출과 무관하게 대상 API가 인증 주체의 권한으로 검사. 서버 비밀정보의 무단 사용·잘못된 목적지 주입도 별도 거절 |
| 서비스 DB 원본이 실행 중 변경됨 | 현재 리소스 기반 요청이 원본 재조회로 몰래 다른 요청으로 바뀌지 않음 |
| 미저장 Query 생성 | 현재 정의로 요청 구성 가능. 저장 여부와 별개로 실행·인증정보 사용 정책 적용 |
| 비밀정보가 없는 직접 접근 가능한 Query | 서버 원본이나 중계 서버 없이 클라이언트 실행 가능 |
| 변조된 요청이 비밀정보를 공격자 URL에 주입하려 함 | 서버가 인증정보 사용 권한·허용 목적지 검증으로 거절 |
| schema와 typeRef 동시 지정 | 검증 오류 |
| 포트 required:true와 객체 schema.required 배열 | 서로 다른 경계에서 검증 |
| State를 Value 포트에 전달 | 값은 읽지만 원본 쓰기 핸들은 받지 않음 |
| 코드형/선언형 Action이 boolean 반환 | /steps/id에서 같은 원시 boolean 읽기 |
| output 없는 native가 값 반환 | 계약 오류와 후속 단계 중단 |
| output 없는 단계의 /steps/id 읽기 | 참조 오류. null 대체 없음 |
| nullable output이 null 반환 | 허용 스키마라면 정상 성공 |
| output 평가 또는 검증 실패 | 실패 결과, 뒤 단계 실행 안 함, 앞 외부 효과 롤백 안 함 |
| 실행 중 같은 on 연결 다시 호출 | 추가 호출 무시, 기존 실행 정보 유지 |
| 소유자 폐기 후 native가 늦게 반환 | 결과/후속 단계 무시, 해당 호출 핸들의 새 쓰기·refresh 거절 |
| slots required 키에 [] 공급 | 유효한 빈 내용 |
| 외부 슬롯 안의 상태 참조 | 작성자 소유 문맥 유지 |
| 공개 이벤트 payload 검증 실패 | 호출자 Action 실행하지 않음 |
| when false 후 true | 기존 내부 인스턴스 폐기 후 새 수명, 외부 상태 유지 |
| repeat 순서만 변경 | key 기준 상태 유지 |
| repeat key 누락·중복 | 오류 |
| Grid 고정 항목 겹침 또는 범위 초과 | 오류, 자동 밀기 없음 |
| Grid 자동 배치와 repeat | 고정 영역 예약 후 원래 확장 순서로 전진 배치 |
| Grid 비활성 when 노드의 layout 키 | 선언은 유효, 공간은 점유하지 않음 |
| 같은 종류의 코드형/선언형 동일 ID 중복 등록 | Component끼리·Action끼리 각각 오류, 숨은 우선순위 없음 |
| 다른 종류의 Query·Component가 같은 ID | 둘 다 등록 가능, xxxRef의 기대 종류로만 해석 |
| 필요한 source 또는 transform 실패 / 정상 빈 결과 | 전자는 Query 전체 실패·부분 성공값 금지·실패 위치 식별, 후자는 성공 |

이 표는 **구현할 인수 테스트의 기대 결과**이며 실제 라이브러리나 machine-readable Schema를 실행해 통과했다는 결과표가 아니다. 구체 오류 코드·시간 제어·어댑터별 렌더링은 구현 검증에서 고정한다.

2026-10-29에 복원한 9개 계약의 추가 기대값은 [인수 백로그 C13–C15·S01–S06·Q13–Q15·A15–A19·L01–L10](../handoff/acceptance-matrix.md)에 있다. 복원 당시에는 미실행 기대값이었으며 현재 독립 실험 결과는 [검증 진행표](../handoff/verification-ledger.md)를 따른다. Assert.message의 필수성·동적 평가/오류 형식, Join 전체 문법과 추가 변환 연산, 새 콜백/DTO/Store/URL SDK는 이 복원으로 확정하지 않는다.

후속 재평가 보완의 C03·C16–C17·Q16–Q17도 같은 인수 백로그에 있으며 현재 독립 실험 증거는 검증 진행표에 연결되어 있다. 등록 범위는 U01에 따른 현재 명확화, Query 실패 의미는 E52에 따른 기존 승인 복원으로 구별한다.

전체 원문 감사 후 복원한 시간·literal·값 비교/snapshot·날짜·초기 완료·갱신 종료·관찰 ID/진단은 같은 [인수 백로그](../handoff/acceptance-matrix.md)의 추가 항목으로 검증한다. 선택 차트의 X 항목은 [별도 모듈 백로그](11-optional-charts.md)에 있다. 이관 대응의 완료 여부는 [전체 대응표](../handoff/source-contract-matrix.md), 아직 구현으로 고정할 공개 계약은 [열린 과제](../handoff/open-contracts.md)에서 판정한다. 어느 표도 실행 통과를 뜻하지 않는다.

## 13 다음 논의의 위치

다음 작업은 확정된 공통 계약을 타입·검증·작은 실행 경로로 옮기는 것이다. 리소스 7종·ports/state·slots·Action 출력·코드 확장·서버 실행 방향을 다시 선택하지 않는다.

**구체화할 공개 계약은 세 묶음이다:** ① 값/스키마의 직렬화와 CEL 적합성 ② 현재 요청을 실행기에 전달하는 DTO·인증정보/오류 경계 ③ 등록·핸들·취소·변경의 최소 SDK와 적합성 테스트. 이는 기능 추가가 아니라 이미 결정한 의미를 구현하는 일이다.
