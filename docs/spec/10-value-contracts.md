# 값 표현 · 시간 · 비교 · 읽기 보호 · 날짜

기준일: 2026-10-29 · 기존 승인 의미 복원과 프로젝트 계약 구체화

[명세 시작점](../VIEWSTEM-SPEC.md) · [Variable·Type](03-variable-type.md) · [이전 승인 이관](09-preserved-contracts.md)

이 문서는 이미 승인한 값 계약을 현재 Variable·Type·StateStore 모델에서 읽을 수 있도록 풀어 쓴다. 새 코드·SDK·스키마 구현이나 실행한 테스트 결과가 아니다. 과거 Channel·Dashboard·compute·DateTransform 등의 이름을 현행 API로 복원하지 않는다. 현재 선언은 `spec.expression`, `variableRef`와 `inputs`, View/Component의 `states` 및 StateStore 계약을 따른다.

## State의 명시적 undefined 저장

**확정(프로젝트 결정 U02):** State의 값 전체로 `undefined`를 명시적으로 저장하려는 쓰기는 오류로 거절한다. 기존 값이 있으면 유지하며, 값 미지정이나 삭제로 변환하지 않는다. 초기값을 지정하지 않아 아직 값이 없는 상태는 명시적인 `undefined` 저장과 구별한다. `null`은 선언 타입이 허용할 때 저장하는 실제 값이다.

이 결정은 JS의 `undefined`가 JSON 경계에서 생략되는 등 저장 의미가 달라지는 것을 방지한다. 코드형 Action의 output 생략에 따른 void 반환 계약은 유지한다. 객체 속성은 아래 U03, 배열 원소·빈 슬롯은 U04, Set 원소는 U05, Map 값은 U06을 따른다. 초기값 없는 State의 읽기 결과는 아래 U07을 따르며, Map key는 기존 string/number 제한을 유지한다. [U02, U03, U04, U05, U06, U07]

## 초기값 없는 State 읽기

**확정(프로젝트 결정 U07):** State가 등록되어 있지만 `initial`이 생략되어 있고 아직 값을 쓰지 않았다면 core는 이를 값 미지정(missing) 상태로 관리하며, JS에서 읽으면 `undefined`를 반환한다. 이 읽기 자체는 오류가 아니다. `undefined`를 State에 저장했다는 뜻이 아니며, State의 존재 여부와 값의 존재 여부를 구분한다. 읽기 때문에 임의의 null·0·false·빈 문자열을 초기값으로 만들지 않는다.

유효한 값을 쓰면 이후 읽기는 그 값을 반환한다. 명시적으로 저장한 `null`은 null을 허용하는 타입의 실제 값이며 missing과 구별한다. 반면 지정한 소유 범위에 등록되지 않은 State 이름을 읽으면 참조 오류이며, 값 미지정으로 숨기거나 State를 자동 생성하지 않는다.

| 조건·행동 | JS에서 관찰할 결과 |
|---|---|
| string 또는 null을 허용하는 selectedDeviceId를 initial 없이 등록한 뒤 읽기 | `undefined`; 등록된 State의 값 미지정 |
| selectedDeviceId에 `"device-1"`을 쓴 뒤 읽기 | `"device-1"` |
| selectedDeviceId에 `null`을 쓴 뒤 읽기 | `null`; 서비스가 선택 해제 등의 의미를 부여할 수 있는 명시 값 |
| 등록하지 않은 selectedDevceId를 읽기 | 참조 오류; 이름 오타를 missing으로 처리하지 않음 |
| 값 미지정 읽기로 얻은 `undefined`를 State 값 전체로 다시 쓰기 | U02의 쓰기 오류; 기존 값 또는 기존 missing 상태 유지 |

읽기 결과로 값 부재를 표현하는 것과 명시적인 undefined 쓰기는 서로 다른 계약이다. 유효한 `0`, `false`, 빈 문자열도 실제 값이며 truthiness로 missing을 판정하지 않는다. 대화 예시의 `readState`·`writeState`는 설명용 이름으로, 이 결정은 실제 SDK 함수명이나 오류 DTO를 확정하지 않는다.

U07은 초기값을 생략한 State의 읽기 결과를 정한다. pending/error·missing의 상세 읽기·관찰은 아래 U13 snapshot을 따른다. CEL·Dart 어댑터의 구체 타입과 적합성 검증은 T1이다. 기존 초기화 대기·늦은 초기값 처리·입력 대기 의미를 변경하거나 모든 값 부재를 일반 undefined 데이터로 바꾸는 근거가 아니다. [U07]

## 객체 속성의 undefined 정규화

**확정(프로젝트 결정 U03):** JS 입력 데이터 객체에서 값이 `undefined`인 속성은 입력으로 허용하되, core가 값을 수용할 때 해당 속성을 생략한 객체로 정규화한다. `undefined`를 core의 독립적인 저장값 종류로 추가하지 않는다. 중첩된 데이터 객체와 배열 안의 객체 속성에도 같은 기준을 적용하며, 속성을 생략한 결과가 빈 객체여도 그 객체 자체를 제거하지 않는다.

정규화한 결과를 기준으로 객체 스키마를 검증한다. 필수 속성이 생략되면 누락 오류이며, 기존 State를 교체하는 쓰기라면 기존 값을 유지한다. `null`은 생략하거나 `undefined`와 합치지 않고 선언 타입이 허용할 때 명시적인 값으로 보존한다. 원본 객체를 직접 수정하지 않는 기존 입력 격리 계약도 유지한다.

| JS 입력 예시 | core가 검증·저장할 값과 결과 |
|---|---|
| `{ name: undefined, age: 20 }`, name은 선택 속성 | `{ age: 20 }` |
| `{ name: undefined, age: 20 }`, name은 필수 속성 | `{ age: 20 }`에 대한 필수 속성 누락 오류 |
| `{ name: null }` | name을 유지하며 null 허용 여부를 타입으로 검증 |
| `{ profile: { name: undefined } }` | `{ profile: {} }`; profile까지 생략하지 않음 |
| `[{ name: undefined }]` | `[{}]`; 배열 원소와 길이는 유지 |

저장값의 읽기·타입별 변경 동등성은 정규화된 값을 기준으로 한다. 따라서 선택 속성만 다른 `{ name: undefined }`와 `{}`는 같은 저장값을 표현한다. 위 예시는 JS 입력이며 JSON 문법 예시가 아니다. 배열 원소 자체의 `undefined`와 sparse array의 빈 슬롯은 아래 U04, Set 원소 자체의 `undefined`는 U05, Map 값 자체의 `undefined`는 U06을 따른다. Map 값이 객체인 경우의 속성 정규화와 Map 엔트리 자체의 생략을 혼동하지 않는다.

**호환성 경계:** JS 서비스가 선택 속성에 `undefined`를 넣는 사용을 수용하면서 JS·Dart·JSON이 공유하는 필드 누락과 null의 구분을 유지하기 위한 결정이다. 다만 `{ name: undefined }`의 키 존재 여부나 `Object.keys()` 결과는 보존하지 않는다. 기존 호스트가 Query 결과 결합 등에서 키 목록을 열 구조로 사용한다면 정규화 전에 열 목록을 확보하고 별도 메타데이터나 스키마로 보존해야 한다. 구체 열 메타데이터 API나 core의 자동 열 추론 기능을 새로 확정하는 것은 아니다. [U03]

## 배열 원소의 undefined와 빈 슬롯

**확정(프로젝트 결정 U04):** 입력 데이터 배열의 원소 자체가 `undefined`이거나 원소가 없는 빈 슬롯(sparse array)이 있으면 core는 그 값을 오류로 거절한다. 객체 속성으로 전달된 배열과 중첩 배열에도 같은 기준을 적용한다. 해당 원소를 제거하여 길이·인덱스를 바꾸거나 자동으로 `null`을 채우지 않는다.

빈자리를 데이터로 표현하려면 호출자가 `null`을 명시하고 원소 타입이 이를 허용해야 한다. 배열 안의 객체 속성은 U03의 정규화를 따르므로 `[{ name: undefined }]`는 `[{}]`로 정규화한 뒤 타입을 검증한다. 객체 원소 자체를 삭제하지 않는다. 기존 State를 교체하는 입력이 이 규칙을 위반하면 쓰기 전체를 거절하고 기존 값을 유지하며, 호출자의 원본 배열도 수정하지 않는다.

| JS 입력 예시 | core의 처리 |
|---|---|
| `[10, undefined, 30]` | 오류; `[10, 30]` 또는 `[10, null, 30]`으로 바꾸지 않음 |
| `[10, , 30]` 또는 `new Array(2)` | 빈 슬롯 오류; 빈 슬롯의 위치나 수에 따라 허용하지 않음 |
| `[10, null, 30]` | null을 허용하는 원소 타입이면 위치·길이·null 보존; 허용하지 않으면 타입 오류 |
| `[]` | 빈 슬롯이 없는 배열; 빈 배열을 허용하는 타입이면 유효 |
| `[{ name: undefined }]` | `[{}]`로 정규화; 객체 타입 검증을 통과해야 수용 |
| `{ rows: [[10, undefined]] }` | 중첩된 배열 원소도 같은 오류; 일부만 적용하지 않음 |

이 결정은 원소 위치를 보존하면서 명시하지 않은 값이 만들어지는 것을 막기 위한 것이다. core는 입력 검증 전에 JSON 직렬화로 `undefined`·빈 슬롯을 null로 자동 치환하지 않는다. 예시는 JS 입력 설명이며 JSON 선언 문법이 아니다. Set 원소는 아래 U05, Map 값은 U06을 따른다. [U04]

## Set 원소의 undefined

**확정(프로젝트 결정 U05):** 입력 데이터의 native Set에 원소 자체가 `undefined`인 항목이 있으면 core는 그 값을 오류로 거절한다. 객체·배열 등 다른 값 안에 중첩된 Set에도 적용한다. 해당 원소를 조용히 제거하거나 `null`로 자동 치환하지 않으며, 기존 State를 교체하는 쓰기라면 전체 쓰기를 거절하고 기존 값을 유지한다. 호출자의 원본 Set은 수정하지 않는다.

| JS 입력 예시 | core의 처리 |
|---|---|
| `new Set([1, undefined])` | 오류; undefined 원소를 제거해 `new Set([1])`로 받아들이지 않음 |
| `new Set([null])` | 원소 타입이 null을 허용하면 명시적인 원소로 보존; 허용하지 않으면 타입 오류 |
| `new Set([{ name: undefined }])` | 객체 속성은 U03에 따라 생략; 빈 객체를 원소 타입이 허용하면 객체 원소 한 개를 유지 |

객체 원소의 속성 정규화와 Set 원소 자체의 거절은 구별한다. 속성을 생략한 뒤 두 객체의 내용이 같아져도 기존 native membership 기준을 유지하며, 별개의 객체 원소를 내용 비교로 합치지 않는다. 입력 격리 후의 객체 참조 의미는 아래 기존 계약을 따른다. [U03, E58, E59]

이 결정은 집합 구성과 크기가 암묵적으로 달라지는 것을 막고, 이미 확정된 [Query 서비스 콜백 전 Set→배열 변환](09-preserved-contracts.md#query-서비스-콜백의-컬렉션-변환)에서도 배열 원소 계약과 일관된 값을 전달하기 위한 것이다. Map 값은 아래 U06을 따르며, 새 Set 변경 API를 함께 확정하는 결정은 아니다. [U05, E47]

## Map 값의 undefined

**확정(프로젝트 결정 U06):** 입력 데이터의 native Map에 값 자체가 `undefined`인 엔트리가 있으면 core는 그 값을 오류로 거절한다. 중첩된 Map에도 같은 기준을 적용한다. 해당 엔트리를 자동 제거하거나 값을 `null`로 치환하지 않는다. 기존 State를 교체하는 쓰기라면 전체 쓰기를 거절하고 기존 값을 유지하며, 호출자의 원본 Map을 수정하지 않는다.

Map key는 기존 계약대로 string 또는 number만 허용하므로 `undefined` key는 이미 금지된다. 숫자 key에도 아래 U08의 유한 숫자 검증을 적용한다. 키를 남기면서 빈값을 표현하려면 호출자가 `null`을 명시하고 값 타입이 이를 허용해야 한다. Map 값이 객체라면 U03에 따라 해당 객체의 undefined 속성만 생략하고 객체 타입을 검증하며, 그 객체를 가리키는 Map 엔트리는 유지한다.

| JS 입력 예시 | core의 처리 |
|---|---|
| `new Map([["a", undefined]])` | 오류; a 엔트리 제거·null 치환 없음 |
| `new Map([[undefined, 1]])` | 기존 key 타입 계약 위반 오류 |
| `new Map([["a", null]])` | null을 허용하는 값 타입이면 키와 명시 null 보존; 허용하지 않으면 타입 오류 |
| `new Map([["a", { name: undefined }]])` | `new Map([["a", {}]])`로 정규화; 빈 객체를 허용하는 값 타입이어야 수용 |

이 결정은 `has(key)`와 `size`로 관찰하는 엔트리 존재 의미를 보존하기 위한 것이다. 객체의 선택 속성 생략 규칙을 Map 엔트리 제거로 확대하지 않는다. [Query 서비스 콜백 전 Map→쌍 배열 변환](09-preserved-contracts.md#query-서비스-콜백의-컬렉션-변환)에서도 승인된 배열 원소 계약과 일관된 값을 전달한다. 초기값 없는 State 읽기는 U07을 따르며, 새 Map 변경 API는 이번 결정으로 확정하지 않는다. [U06, E47, E58]

## 유한 숫자만 허용

**확정(프로젝트 결정 U08):** core가 데이터 값으로 수용하는 숫자는 유한한 수여야 한다. `NaN`, `Infinity`, `-Infinity`는 오류로 거절하며 `0`·`null`·문자열로 자동 변환하거나 필드·원소·엔트리를 제거하지 않는다. 객체 속성, 배열·Set 원소, Map 값 및 숫자 key에도 같은 검증을 적용한다.

외부에서 들어온 값뿐 아니라 표현식·변환 등의 결과를 core 데이터로 수용할 때에도 이 기준을 적용한다. 비유한 수를 포함한 State 쓰기는 전체를 거절하고 기존 값 또는 missing 상태를 유지하며, 호출자의 원본을 수정하지 않는다. 계산 결과가 거절되면 해당 계산의 기존 실패 전파 계약을 따르고, 정상 값으로 성공 처리하지 않는다. 이 결정으로 실행기 내부의 중간 연산이나 오류 모델을 별도로 재정의하지 않는다.

| JS 값 예시 | core의 처리 |
|---|---|
| `NaN`, `Infinity`, `-Infinity` | 비유한 숫자 오류 |
| `{ ratio: NaN }`, `[Infinity]`, `new Set([-Infinity])` | 중첩된 비유한 숫자도 오류; 일부만 제거하거나 치환하지 않음 |
| `new Map([["ratio", NaN]])`, `new Map([[Infinity, 1]])` | Map 값·숫자 key 모두 오류 |
| JS에서 `0 / 0`, `1 / 0`으로 얻은 결과 | 각각 NaN·Infinity이므로 core 값으로 수용할 때 오류 |
| `0`, `-1`, `1.25` | 유한성 검사는 통과; 나머지 선언 타입·스키마 제약은 별도 검증 |
| 문자열 `"NaN"`, `"Infinity"` | 비유한 숫자가 아닌 문자열; 문자열 타입이 허용하면 그대로 유지하고 숫자로 암묵 변환하지 않음 |

비유한 수는 JSON 숫자로 직접 표현할 수 없으며, 자동 null·0 치환은 계산 오류와 명시적인 데이터·결측값을 섞는다. core는 검증 전에 직렬화로 비유한 수를 null로 바꾸어 수용하지 않는다. 유한성은 숫자에 대한 최소 조건이며, integer의 범위는 아래 U09, number의 표현·자동 반올림 금지는 U10을 따른다. CEL·JS·Dart 간 구체 숫자 대응은 별도 구체화 대상이다. [U08, U09, U10]

## integer의 안전 정수 범위

**확정(프로젝트 결정 U09):** `integer`로 검증되는 값은 유한한 숫자이면서 분수부가 없는 정수여야 하고, JS 안전 정수 범위인 **-9,007,199,254,740,991 이상 9,007,199,254,740,991 이하**여야 한다. 양쪽 끝값을 포함하며, 이는 `-(2^53 - 1)`부터 `2^53 - 1`까지다. 선언 스키마의 추가 제약도 함께 적용한다.

범위를 벗어나거나 정수가 아닌 값은 오류로 거절한다. 반올림·잘라내기·범위 끝값으로 제한하기·문자열 변환으로 받아들이지 않는다. 기존 State의 integer 값 검증이 실패하면 전체 쓰기를 거절하고 기존 값 또는 missing 상태를 유지하며, 호출자의 원본을 수정하지 않는다. 객체 속성·컬렉션 원소 등 중첩 위치나 계산 결과에도 해당 값이 integer로 검증되는 곳에서는 같은 기준을 적용한다.

| 값과 선언 타입 | core의 처리 |
|---|---|
| integer의 `-9007199254740991`, `0`, `9007199254740991` | 공통 integer 검사를 통과; 나머지 스키마 제약도 검증 |
| integer의 `-9007199254740992`, `9007199254740992` | 범위 오류 |
| integer의 `1.5` | 정수 타입 오류; 1이나 2로 보정하지 않음 |
| integer에 문자열 `"42"` 전달 | 타입 오류; 숫자로 암묵 변환하지 않음 |
| string에 문자열 `"9007199254740993"` 전달 | 문자열 계약으로 검증하고 그대로 보존; integer로 자동 변환하지 않음 |
| integer로 수용할 계산 결과가 `9007199254740992` | 결과 검증 오류; 해당 계산의 기존 실패 전파 계약 적용 |

이보다 큰 정수 식별자는 처음부터 문자열 타입으로 선언해 정확한 문자열로 전달한다. 이미 숫자로 읽으며 잃은 정밀도를 문자열 변환으로 복구할 수 있다는 보장은 없다. 이 범위는 언어별 실행기가 더 넓은 정수를 표현할 수 있더라도 core의 integer 계약에 동일하게 적용한다. CEL 실행기의 내부 정수 범위는 별도이며, core 데이터로 전달되는 BigInt의 거절은 아래 U12를 따른다.

U09는 integer로 검증되는 값의 범위다. number의 표현은 아래 U10을 따르며 CEL·JS·Dart 간 구체 변환은 별도 구체화 대상이다. Map의 기본 숫자 key 계약을 integer 선언으로 바꾸지 않으며, 기존 string/number 구분과 U08의 유한성 검증을 유지한다. [U09, U10]

## number의 표현과 자동 반올림 금지

**확정(프로젝트 결정 U10):** `number`는 JS Number와 같은 IEEE 754의 64비트 부동소수점(binary64)으로 표현한다. U08의 유한성 제한을 함께 적용하므로 NaN·Infinity·-Infinity는 여전히 거절한다. `integer`로 검증하는 값에는 U09의 안전 정수 범위를 추가로 적용하며, 그 범위를 모든 number의 크기 제한으로 확대하지 않는다.

core는 number를 수용·저장·읽을 때 소수 자릿수를 임의로 제한하거나 추가 반올림·절사·오차 보정을 하지 않는다. 이 규칙은 중첩된 숫자 값과 Map의 숫자 key, core 데이터로 수용할 계산 결과에도 적용한다. 선언 스키마의 검증은 유지하며, 검증에 맞추려고 값을 보정하지 않는다. 기존 입력 격리와 실패한 State 쓰기의 원자성도 유지한다.

자동 반올림 금지는 binary64 자체의 이진 근사 표현과 연산에 수반되는 반올림까지 없앤다는 뜻이 아니다. 십진 소수를 항상 정확하게 표현하거나 계산한다고 보장하지 않는다. 필요한 반올림은 호출자가 계산 단계에서 명시적으로 수행하고, 표시 자릿수는 표시 단계에서 지정한다. 표시 형식만 바꾸는 일을 저장값의 자동 변경으로 연결하지 않는다. 구체 반올림·표시 함수의 이름이나 카탈로그를 새로 확정하는 것은 아니다.

| 입력·결과와 선언 타입 | core의 처리 |
|---|---|
| number에 JS `0.1 + 0.2`의 결과 입력 | `0.30000000000000004`로 유지; 자동으로 `0.3`으로 보정하지 않음 |
| 호출자가 명시적으로 반올림한 number `0.3` 입력 | 해당 스키마를 만족하면 전달받은 `0.3`을 유지 |
| `{ ratio: 0.30000000000000004 }`, 배열·Set 원소·Map 값·숫자 key의 같은 숫자 | 중첩 위치에도 추가 소수 반올림 없음; 원본을 수정하지 않음 |
| number에 유한한 `1e100` / integer에 같은 값 입력 | 전자는 number 표현·유한성 검사를 통과한 뒤 나머지 스키마 검증; 후자는 U09 범위 오류 |
| JS `Number.MAX_VALUE * 2`의 결과를 number로 수용 | Infinity이므로 U08의 오류; 유한한 최댓값으로 제한하거나 null로 바꾸지 않음 |

JS 서비스가 사용하는 숫자 표현과 core의 값 표현을 맞추면서, 도메인마다 다른 반올림 자릿수·시점을 core가 임의로 정하지 않기 위한 결정이다. 정확한 십진 연산 타입을 추가한 승인은 아니며, core 데이터의 BigInt는 U12에 따라 거절한다. `-0`은 아래 U11에 따라 `0`으로 정규화한다. 구체 숫자 직렬화·CEL/JS/Dart 어댑터는 별도 구체화 대상이며, 어댑터는 이 number 표현 계약을 만족해야 한다. CEL 실행기 내부 연산·지원 함수 전체의 적합성을 이번 결정만으로 확인한 것으로 보지 않는다. [U10, U11, U12]

## 음수 0의 정규화

**확정(프로젝트 결정 U11):** core는 데이터 값으로 받아들이는 숫자 `-0`을 양의 0인 `0`으로 정규화한다. `number`와 `integer` 모두에 적용하며, State 초기값·쓰기와 core 데이터로 수용할 계산 결과에도 같은 기준을 적용한다. 객체 속성, 배열·Set 원소, Map 값과 숫자 key 등 중첩 위치도 포함한다. 읽기 결과에서 음수 0의 부호를 보존하지 않는다.

정규화한 값을 기준으로 선언 스키마를 검증하고 변경 여부를 비교한다. 기존 값이 `0`인 State에 `-0`을 쓰는 것만으로 실제 값 변경을 만들지 않으며, 그 차이만을 이유로 updated 통지나 의존 계산·reaction·Query 재실행을 발생시키지 않는다. 정의·수명 교체의 `replaced` 통지는 기존 별도 계약을 유지한다. 0을 허용하지 않는 스키마라면 정규화한 값도 오류이며, 쓰기 전체를 거절하고 기존 값 또는 missing을 유지한다.

호출자의 원본은 수정하지 않고 격리된 값에 정규화를 적용한다. 객체·배열의 내용 비교와 Set의 native membership·Map의 key 비교 기준은 유지한다. 특히 별개의 객체 Set 원소가 정규화 후 같은 내용을 갖더라도 내용 비교로 합치지 않는다. JS native Set 원소·Map key의 `-0`과 `0`은 입력 컬렉션에서부터 같은 항목으로 취급되므로, 이번 결정이 별도의 중복 Map key 처리 규칙을 추가하는 것은 아니다.

| 입력·행동 | core의 처리 |
|---|---|
| number 또는 integer에 `-0` 입력 | 0을 허용하는 스키마이면 양의 `0`으로 수용·읽기; JS `Object.is`로 읽은 값을 `-0`과 비교하면 false |
| 값이 `0`인 State에 `-0` 쓰기 | 값 변경 없음; 이 차이로 updated 통지·의존 실행을 만들지 않음 |
| `{ offset: -0 }`, `[-0]`, `new Map([["offset", -0]])` | 각각 `{ offset: 0 }`, `[0]`, `new Map([["offset", 0]])`; 원본의 음수 0은 수정하지 않음 |
| `new Set([-0, 0])`, `new Map([[-0, "value"]])` | 숫자 `0` 원소 하나, 숫자 `0` key의 엔트리 하나; 기존 native membership 유지 |
| JS `Math.round(-0.1)`의 결과를 core 데이터로 수용 | 결과 `-0`을 `0`으로 정규화; core가 추가 반올림을 실행하는 예시가 아님 |
| 유한한 음수 `-0.0001` / 문자열 `"-0"` | 각각 해당 숫자 / 문자열로 유지; 작은 수를 0으로 반올림하거나 문자열을 숫자로 바꾸지 않음 |

JS의 JSON 직렬화가 음수 0을 `0`으로 기록하고 native Set·Map도 두 0을 구별하지 않는 경계와 맞추기 위한 선택이다. 따라서 음수 0의 부호를 이용하는 계산의 구분은 core 데이터 경계를 넘어 보존하지 않는다. U10의 자동 반올림 금지를 일반적인 오차 보정으로 완화하지 않으며, 오직 실제 숫자 `-0`에 적용한다. CEL 실행기의 내부 중간 연산 전체를 다시 정의하거나 구체 직렬화·오류 DTO를 새로 확정하는 결정은 아니다. [U11]

## 값 검증의 공통 기본 규칙

**확정(세부 판단 위임 U12에 따른 일괄 결정):** 사용자는 기존 방향에서 자연스럽게 정해지는 세부 계약을 담당자가 결정하도록 위임했다. 아래는 그 위임에 따른 설계 선택이며, 각 항목을 사용자가 개별 승인한 것으로 기록하지 않는다.

| 경계 | v1의 공통 규칙 |
|---|---|
| 미지원 런타임 값 | 데이터로 전달되는 BigInt·Symbol·함수·Promise·WeakMap·WeakSet은 최상위와 중첩 위치 모두 오류. 숫자·문자열·빈 객체·null로 바꾸거나 해당 필드를 삭제하지 않음. 작은 BigInt도 동일하게 거절 |
| 순환 데이터 | 객체·배열·Set·Map의 데이터 참조를 따라 자기 자신으로 돌아오는 순환은 오류. 순환 참조를 끊거나 생략해 받아들이지 않음. 동일 객체를 여러 위치에서 재사용하는 비순환 구조는 허용하며, 위치·원소 수를 보존 |
| 스키마 검증 | 검증은 타입과 제약을 확인하는 일. 문자열을 숫자·boolean으로 바꾸거나 schema.default를 주입하거나 허용되지 않은 속성을 자동 제거하지 않음. 추가 속성의 허용 여부는 선언 스키마를 따름 |
| 수용 순서 | 원본과 격리한 입력에 승인된 정규화(U03의 객체 속성 undefined 생략·U11의 음수 0 정규화)를 적용하고, 유효성 검증 후 변경 비교·값 반영·통지를 수행. 실패한 State 쓰기는 정규화 중간값도 노출하지 않고 전체 거절 |
| 숫자 변경 비교 | 정규화된 유한 숫자의 실제 값을 정확히 비교. core 공통 허용 오차나 epsilon을 두지 않음. `0.3`과 `0.30000000000000004`는 다른 값이며, 필요한 반올림·허용 오차 판단은 명시적인 계산으로 수행 |

미지원 값의 거절은 **데이터 경계**에 적용한다. 등록된 코드형 Component/Action의 함수, 실행 완료를 나타내는 비동기 Promise, State/Query 포트의 명시적 핸들은 각각 기존 실행·연결 계약을 따른다. 데이터 안의 함수를 호출하거나 Promise를 자동으로 기다려 저장값으로 바꾸지는 않는다. 이미 지원하기로 한 native Set/Map의 의미는 유지한다. 날짜 값은 아래 U14의 문자열 계약을 따르며 호스트의 날짜 객체를 그대로 저장하는 예외를 두지 않는다.

순환 검출은 데이터 참조에 대한 규칙이며 리소스 참조 그래프나 Action 재귀의 지원 범위를 결정하지 않는다. 비순환 공유 객체를 수용한다는 것이 외부 원본 identity나 모든 위치의 읽기 참조 동일성을 보장하는 것은 아니며, 기존 입력 격리·Set membership·안정 snapshot 계약을 유지한다.

실패 위치와 원인을 식별할 수 있게 하되 오류 코드·경로 DTO·진단 문구의 구체 형식은 구현 담당자가 기존 오류 전파 계약에 맞춰 정한다. Query·Action의 비동기 실패, 이미 완료한 다른 State 쓰기나 외부 효과의 비롤백 경계는 바꾸지 않는다. 위 규칙은 자동 변환으로 데이터 의미를 숨기지 않고 언어 간 재현 가능한 값 경계를 유지하기 위한 선택이다. [U12]

## 값 표현과 literal 데이터

**확정:** 동적 값 표현은 `@path`로 값을 읽고 `@call`로 허용된 함수를 호출한다. 단일 `@path` 참조는 원래 값의 타입을 유지하고 `formatString`은 문자열을 만든다. 각 리소스의 실행 문맥에서 허용한 데이터와 함수만 사용할 수 있다. 같은 문법이 다른 리소스의 내부 상태 접근이나 쓰기 권한을 부여하지 않는다. [E22, E31]

일반 데이터의 `path`·`call` 키를 표현식으로 해석하지 않는다. 동적 값 영역에서 실제 `@`로 시작하는 데이터 키를 표현할 때에는 승인된 `@@` 이스케이프를 유지한다. 예를 들어 `@@path`는 데이터 키 `@path`를 나타내기 위한 표기이며 값 참조를 실행하는 지시가 아니다. HTTP 주소 `request.path`와 과거 실행 위치 `target.path`의 이름을 `@path`로 바꾸는 규칙도 아니다. [E54]

표현식의 적용 위치·재귀·오류는 다음 U13 프로필을 따른다. reaction의 고정 JSON 상수처럼 계산식으로 해석하지 않기로 한 자리는 해당 자리의 계약을 유지한다. A2UI의 전체 surface·카탈로그·전송 모델을 채택해야 이 표기를 쓸 수 있다는 뜻은 아니다.

### 동적 값 평가 프로필

**확정(U13):** 동적 영역은 호출 위치 inputs의 Value 값, State.initial, HTTP baseUrl·method·path·headers·params·body 및 Login request/token, Query transform.input·Concat.with·Join.right, Action value·condition·output.value·Assert.message, 노드 when·repeat.items/key·emit.payload, Query 사용의 executeWhen/autoRefreshWhen이다. State/Query 포트 입력과 SetState/RefreshQuery target은 같은 @path 표기로 **대상 핸들만** 해석한다. 스키마·ID·xxxRef·이벤트 이름·Variable의 CEL 소스·포트 default·reaction의 고정 value는 일반 값 평가로 재해석하지 않는다.

동적 영역의 원래 객체·배열을 재귀 평가한다. `{"@path":"..."}`는 그 키만, `{"@call":"함수명","args":...}`는 그 두 키만 가진 표현식이다. 예약 키와 일반 필드 혼합·두 연산자 동시 사용·알 수 없는 단일 @ 예약 키는 INVALID_EXPRESSION이다. 일반 데이터의 @ 키는 @@로 한 번 이스케이프하고, 해제 후 키 충돌은 오류다. 해제한 객체나 @path/@call이 **반환한 데이터**를 다시 표현식으로 실행하지 않는다. native Set/Map 내부 데이터도 표현식 문법 트리로 재해석하지 않는다.

@path는 [JSON Pointer](https://www.rfc-editor.org/rfc/rfc6901.html)의 절대 경로 표기를 사용하고 `~0`·`~1`로 키의 ~·/를 이스케이프한다. 현재 문맥이 허용하는 /ports·/states·/queries·/steps·/event·/repeat·/actions 등의 루트만 읽으며 /secrets와 /auth/token은 승인된 HTTP 요청 구성 문맥으로 제한한다. auth.token 추출은 해당 Login 응답 /response만 읽으며 요청 입력이나 secret 문맥을 공유하지 않는다. 객체의 own 속성과 배열의 존재하는 정수 인덱스만 순회하고 prototype 탐색은 하지 않는다. Set/Map 원소를 문자열 경로로 암묵 조회하지 않는다. 등록하지 않은 리소스·State·단계 이름은 참조 오류이고, 유효한 데이터 객체의 없는 선택 속성은 missing이다. 중간 값이 null이거나 잘못된 컨테이너이면 경로 타입 오류다.

**배열의 경로와 크기(U24):** 배열 경로의 인덱스는 `0` 또는 0으로 시작하지 않는 십진 정수 표기이며 실제 원소가 존재해야 한다. `/length`·사용자 추가 속성·`01`·음수·소수·범위 밖 인덱스는 배열 원소로 읽지 않는다. 일반 객체의 `length`나 `01` 데이터 키는 이 배열 전용 제한을 받지 않는다. 배열 크기는 [Variable의 CEL `size` 계산](03-variable-type.md#배열-크기-계산)을 사용한다. U23의 P41 실패는 U24에서 실험 평가기의 배열/객체 분기를 수정하고 Node/실제 Chromium에서 검증했다. [수정 전 증거와 현재 결과](../handoff/t2-http-boundary-2026-10-29.md)는 보존하며 core 전체 표현식 구현 완료로 확대하지 않는다.

**U25 문제의 수정·검증(U26):** headers 객체 전체 @path를 정적 헤더 이름으로 오인하던 P51은 [HTTP 헤더 계약](01-datasource-auth.md#http-전송-프로필과-현재-요청-dto)에 맞게 수정했다. 정적 금지 이름은 Login 전에, 동적 참조 결과는 해당 요청 전·병합 전에 검사하며 반환 데이터를 재평가하지 않는다. Node/실제 Chromium에서 정상 참조·금지 이름·중복·제거를 검증했다.

**U26 문제의 수정·검증(U27):** request.path의 @path를 평가하지 않던 P61은 [HTTP 주소 계약](01-datasource-auth.md#http-전송-프로필과-현재-요청-dto)에 맞게 수정했다. 평가한 문자열에 기존 주소 문법·공통 경로·목적지 권한 검사를 적용하고, 목적지 확정 전에는 secret resolver를 제공하지 않는다. Node/실제 Chromium에서 정상 경로·금지 주소·권한 거절을 확인했다.

**U28 전체 경로 점검:** P71의 Datasource.baseUrl과 method·Login request 전체의 평가 누락을 고쳤다. 공통 평가기로 엄격한 표현식 형태, @@ 한 번 해제, 재귀 평가와 반환 데이터 비재실행, JSON Pointer·허용 문맥·타입 구분, concat/formatString을 연결했다. [검사 위치 17개와 실행 증거](../handoff/t2-path-audit-2026-10-30.md)는 HTTP 독립 실험의 범위다. State·Action·UI의 동적 영역, 대상 핸들, 반응형 snapshot·추가 함수 등록은 미구현이며 이 결과를 core 전체 통과로 확대하지 않는다.

**HTTP 명시 실행의 경로 오류(U28):** 잘못된 Pointer·표현식 형태는 INVALID_EXPRESSION, 허용되지 않은 루트·선언되지 않은 포트·잘못된 배열 인덱스는 REFERENCE_NOT_FOUND다. 유효한 데이터 객체의 없는 선택 속성은 missing이므로 현재 값을 요구하는 HTTP 실행에서는 INPUT_NOT_READY로 거절한다. null·스칼라·native 컬렉션 내부를 객체처럼 순회하면 TYPE_MISMATCH다. 문자열로 강제 변환하거나 빈 값으로 전송하지 않는다. Login 응답의 토큰 속성이 없는 경우도 INPUT_NOT_READY로 후속 API를 막는다. 이는 State의 missing 읽기·자동 Query의 waiting을 오류로 바꾸는 규칙이 아니다.


v1 @call 기본 함수는 `concat`과 `formatString`으로 고정한다. concat은 문자열 args 배열을 받아 순서대로 이어 붙이며 빈 배열은 빈 문자열이다. formatString은 `{value: 문자열}`을 받고 `${/절대/경로}`를 문자열·유한 숫자·boolean·null의 문자 표현으로 치환한다. `$$`는 리터럴 `$`이고 잘못된 보간식·객체/컬렉션 보간은 오류다. missing/pending/error는 문자열 "undefined"나 빈 문자열로 숨기지 않고 입력 준비·실패 규칙을 따른다. 추가 순수 함수는 이름·인자·결과 스키마를 명시 등록하고, 미등록 함수나 인자 형태 불일치는 오류다. 이 concat 함수와 Query의 Concat 단계는 별개다.

### 값 준비 상태의 읽기

**확정(U13):** 상세 읽기 snapshot은 `status: missing | pending | ready | error`로 구분한다. ready에만 value가 있으며 null·false·0도 실제 value다. error에는 공통 오류가 있고 pending은 아직 준비 중임을 뜻한다. missing을 데이터 null이나 JSON에 실을 undefined 값으로 바꾸지 않는다.

JS의 간단 읽기는 ready의 값, missing의 undefined를 반환하고, pending이면 VALUE_PENDING, error이면 원인 오류를 던진다. 자동 의존성 평가는 이 예외를 사용자 오류로 바꾸기보다 상세 snapshot으로 대기·실패를 연결한다. Dart·전송 어댑터는 이 구분을 보존해야 하며 구체 언어별 타입은 적합성 검증 대상이다. State 제거는 명시적 제거 연산이며 null·undefined 쓰기와 구별한다. [U07, U13]

## 시간 입력과 재평가

**보존할 확정 의미:** ‘오늘인가?’ 같은 시간 의존 계산에 현재 시각을 공급하고, 시간이 바뀌면 의존 계산을 다시 평가하는 기능을 유지한다. CEL 도입은 이 연결을 삭제한 결정이 아니다. 다른 Variable의 결과를 `inputs`에 전달해 재사용하는 연결도 유지한다. [E53]

현재 모델에서는 필요한 시간을 명시적인 Value 입력으로 연결한다. Variable은 전달받은 port 값으로 계산하며 CEL 안에서 StateStore나 숨은 전역 clock을 암묵 조회하지 않는다. 시간 입력이 바뀌면 그 입력에 의존하는 계산과 후속 실행 판단을 갱신한다. CEL 자체의 중첩 계산과 Viewstem 리소스 간 참조·입력 연결을 혼동하지 않는다.

시간 공급자 API·수명은 U13의 Clock 계약을 따르고 재평가 빈도는 명시적인 공급자가 소유한다. 시간대·달력 경계는 아래 U14의 명시 업무 시간대를 따른다. 고정된 core 기본 주기를 새로 정하지 않는다. 서비스가 선택 날짜/시간을 현재 시각에 맞춰 계속 움직이거나 LIVE 상태를 관리하는 책임을 이 계약만으로 core에 옮기지 않는다. State 초기값·reset의 고정 baseline은 별도 계약이므로 시간 변화마다 초기값을 다시 실행하지 않는다.

## 타입별 변경 동등성

**확정:** 변경 여부를 모든 값에 대한 JS 참조 비교 하나로 결정하지 않고 선언 타입에 맞춰 비교한다. 암묵적인 문자열/숫자 변환으로 값을 같게 만들지 않는다. [E58]

| 값 | 변경 동등성의 확정 의미 |
|---|---|
| 숫자 | U12에 따라 유한한 실제 값을 정확히 비교하며 허용 오차 없음. `-0`과 `0`은 U11 정규화 후 같은 값 |
| 객체 | 속성 이름과 내용을 비교하며 속성 나열 순서는 무시. 포함된 값도 해당 타입의 기준을 적용 |
| 배열 | 내용과 원소 순서로 비교. 순서 변경은 의미가 있음 |
| native Set | primitive 값과 동일 객체 참조에 대한 native membership 기준. 삽입 순서는 무시 |
| native Map | key는 string 또는 유한한 number(U08). key와 해당 값의 대응을 비교하고 값에는 타입별 재귀 비교를 적용. 삽입 순서는 무시 |

객체를 원소로 가진 Set을 객체 내용 기반의 집합으로 바꾸지 않는다. Map의 string/number key 범위를 ‘모든 primitive key’로 확대하지 않는다. 객체 Set의 참조는 아래 입력 격리 후 저장된 값의 참조라는 경계와 함께 해석한다.

이 기준은 State의 실제 변경 감지와 의존 계산·reaction·Query의 실행 판단에 연결한다. 정의·수명 교체를 알리는 `replaced`는 값이 같더라도 통지한다는 별도 StateStore 관찰 계약을 유지한다. 읽기 전용 값의 잘못된 직접 변이를 조용히 성공이나 무변경으로 처리하지 않고 오류로 드러낸다. 오류 DTO는 U13의 공통 계약을 따르며 보호 구현 방식·CEL/Dart의 동일 의미는 기술 검증 T1–T3에 남는다. JS 객체의 물리적 참조를 다른 언어에 그대로 전달한다는 약속은 아니다.

## 입력 격리와 읽기 snapshot

**확정:** 서비스나 호출자가 전달한 원본을 격리해 보호한다. 원본 객체 자체를 freeze해서 보호를 구현하지 않으며, 격리된 저장값이 원본과 같은 identity를 갖는다는 보장은 없다. 반환된 값을 직접 변이해 State 쓰기·검증 경로를 우회할 수 없어야 한다. [E59]

| 경계 | 확정 의미 |
|---|---|
| 변경 없는 읽기 | 같은 값의 변경 없는 연속 읽기는 같은 보호된 참조를 반환 |
| 과거 읽기 | 이미 반환한 snapshot은 이후 변경 때문에 내용이 바뀌지 않음 |
| 원본 보호 | 입력 원본을 freeze하거나 변형하지 않고 격리. 원본을 나중에 편집해 저장값을 몰래 바꾸지 못함 |
| 객체 Set | membership 판단과 허용된 변경 경로에서의 객체 식별은 저장된 참조를 기준으로 함. 외부 원본 객체로 `has`/`delete`가 동작한다는 보장 없음 |
| 같은 외부 객체 재입력 | 외부 원본을 다시 전달했을 때 이전의 격리된 저장 참조와 동일하다는 보장 없음 |

객체 Set 설명은 보호된 읽기 Set에서 `delete` 같은 변이를 허용한다는 뜻이 아니다. 실제 변경은 허용된 State 변경 경로를 거쳐야 하고, 잘못된 직접 변이는 오류로 드러낸다. 고정된 snapshot과 같은 참조의 안정 읽기를 함께 만족시키는 복사·proxy·자료구조 선택은 구현 상세다. 매 읽기 전체 deep copy나 특정 freeze/proxy 기법을 계약으로 강제하지 않는다.

StateStore 관찰값도 이 런타임 값·보호 정책을 따른다. [Query 서비스 콜백 전 Set/Map 재귀 변환](09-preserved-contracts.md#query-서비스-콜백의-컬렉션-변환)은 별도 전송 경계이며, 관찰값을 전송용 배열로 바꾸거나 과거 snapshot을 변경하는 근거가 아니다. [E45, E47]

## 날짜 계산과 포맷의 보존 경계

**보존할 확정 의미:** date·time·datetime의 구분과 format 검증을 유지한다. 기존 날짜 add의 인자는 정수로 검증하고 정수가 아닌 값을 임의 반올림·잘라내기로 받아들이지 않는다. CEL 도입 후 이 기능을 연결하는 날짜 함수에도 기존 의미를 이관한다. 함수 이름·등록 방식이나 과거 DateTransform JSON을 그대로 확정하는 것은 아니다. [E60]

YY 해석의 승인된 경계는 다음과 같다. 특정 패키지의 ‘기본값’을 다시 조사해야만 결과를 알 수 있게 두지 않는다.

| YY | 해석 결과 |
|---|---|
| 00–68 | 2000–2068 |
| 69–99 | 1969–1999 |

E60에서 합의한 datetime 패턴은 `YYYY-MM-DD[T]HH:mm:ss.SSS[Z]`다. E60만으로 모든 내부 값·codec까지 확정됐다고 해석하지 않으며, 아래 U14가 현행 날짜 타입의 적용 경계를 새로 확정한다.

### 날짜 값과 전송 형식

**확정(U14):** date·time·datetime의 core 공개 값은 문자열이다. JS Date·Dart DateTime·날짜 라이브러리 객체를 State에 그대로 저장하거나 epoch 숫자로 암묵 변환하지 않는다. 호스트 어댑터가 종류·시간대를 명시해 문자열로 바꾼 후 전달한다. core 내부 계산 자료구조는 구현 선택이지만 읽기·출력·snapshot·HTTP/URL 경계에서 같은 의미와 정규 문자열을 보장한다.

| 논리 타입 | 의미·수용 입력 | 정규 값 예시 |
|---|---|---|
| date | 시간대 없는 달력 날짜. 실제로 존재하는 `YYYY-MM-DD` | `2026-10-29` |
| time | 날짜·시간대 없는 하루 안의 시각. `HH:mm`, `HH:mm:ss`, 또는 초 뒤 1–3자리 소수 | `09:30:00.000` |
| datetime | 절대 시점. `YYYY-MM-DDTHH:mm:ss`와 선택적 1–3자리 소수, 필수 `Z` 또는 `±HH:mm` offset | `2026-10-29T00:30:00.000Z` |

연도는 0001–9999의 그레고리력, 시는 00–23·분/초는 00–59를 사용한다. 실제 달력·offset을 검사하며 잘못된 날짜의 자동 이월, 24:00, 윤초, 알 수 없는 offset을 뜻하는 -00:00은 거절한다. 소수 초는 밀리초까지 0으로 채우고 초과 정밀도는 반올림하지 않고 거절한다. datetime은 offset을 적용해 UTC로 정규화하며 결과도 연도 범위 안이어야 한다. 이 프로필은 [RFC 3339](https://www.rfc-editor.org/rfc/rfc3339.html)의 전체 수용 범위를 약속하는 것이 아니라 Viewstem의 제한된 날짜 입력 계약이다.

예를 들어 `2026-10-29T09:30:00+09:00`은 `2026-10-29T00:30:00.000Z`가 된다. `2026-10-29`는 시간대에 따라 전날로 이동하지 않으며, offset 없는 `2026-10-29T09:30:00`을 datetime으로 받아 브라우저 시간대를 붙이지 않는다. date와 time을 결합해 절대 시점으로 바꾸는 작업은 아래 업무 시간대를 명시한 별도 변환이다.

이 규칙은 `x-viewstem-type`으로 선언한 날짜 값과 명시적 날짜 변환 함수의 결과에만 적용한다. 일반 string·HTTP의 미지정 응답 문자열을 날짜처럼 보인다는 이유로 변환하지 않는다. 선언된 날짜는 수용 경계에서 형식 검사·정규화한 뒤 나머지 검증·변경 비교·commit을 수행한다. 같은 시점을 다른 offset으로 입력해도 정규 값이 같으면 실제 State 변경이 아니다. 기존 const/enum·포트 default 같은 스키마 상수는 정규 형식으로 작성하며 검증 중 상수를 자동 고치지 않는다. 날짜 정규화가 있는 스키마 조합은 단일 정규 값을 결정할 수 있어야 한다. 이를 위해 같은 값 위치에서 문자열을 허용하는 모든 분기는 같은 날짜 종류를 선언해야 한다. 날짜와 null의 anyOf는 허용하지만 날짜와 일반 string의 혼합처럼 분기별 정규화가 달라지는 조합은 등록 오류다.

U32의 [직접 날짜 어댑터 후속 검증](../handoff/boundary-followup-2026-10-30.md)에서 정규화 후 const/enum/pattern/길이 검사를 생략하던 문제와 지역 시각 변환 결과의 연도 범위 검사를 보완했다. CEL 내부 날짜 함수나 전체 스키마 조합의 적합성으로 확대하지 않는다.

**U34 기술 보완:** Map의 string key에 날짜 스키마를 적용하여 서로 다른 입력 key가 같은 정규 문자열이 되면 해당 값 수용 전체를 거절한다. 먼저/나중 엔트리를 선택해 값을 잃게 하지 않는다. native JS Map이 입력 시점에 이미 합친 숫자 -0/0과 달리, 이 경우는 core 정규화에서 발생한 충돌이다. 위임된 값 수용 경계의 보완이며 Map 객체 원소의 내용 동등성 규칙을 바꾸지 않는다.

HTTP·서비스 콜백·URL은 정규 문자열을 기존 JSON/스칼라 codec으로 전달하고 별도 날짜 태그 객체나 epoch 숫자로 바꾸지 않는다. JSON 복원 시 대상 날짜 스키마로 다시 검증한다. CEL·Dart 어댑터도 명시 날짜 타입과 일반 문자열을 구별하며 같은 정규화·오류 결과를 제공해야 한다. 함수 목록·패키지와 실제 교차 실행 결과는 T1에서 검증한다.

### 명시 업무 시간대와 달력 연산

**확정(U14):** 서비스가 [IANA 시간대](https://www.iana.org/time-zones) 이름(예: `Asia/Seoul`)을 명시적 Value 입력으로 제공한다. View/Component/Variable/Action이 필요로 하는 포트와 날짜 함수의 인자로 연결하며 브라우저·서버 로컬 시간대나 숨은 runtime 전역 기본값을 사용하지 않는다. 입력 이름은 서비스의 포트 계약으로 정하고, 동일 기능이 쓰는 시간대는 같은 서비스 입력에 연결한다. 시간대 변경은 일반 입력 변경으로 의존 계산·Query의 세대 검증을 거친다.

date/time 저장·검증과 offset 있는 datetime의 UTC 정규화에는 업무 시간대가 필요 없다. ‘오늘’, 지역 날짜·하루의 경계, date+time→datetime처럼 지역 달력 해석이 필요한 연산에는 필수다. 시간대 인자 누락은 정의 검증 오류, 연결한 입력이 missing/pending이면 기존 자동 평가 대기·명시 호출 INPUT_NOT_READY 규칙, 유효하지 않거나 지원하지 않는 IANA 이름은 값 오류로 처리한다. 임의 UTC·기기 시간대로 대체하지 않는다. 현재 시각 자체도 Clock에서 명시 입력으로 전달한다.

달력상의 하루 증감과 24시간의 경과량 증가는 서로 다른 연산이다. 업무 시간대의 다음 날 경계를 구할 때 고정 86,400,000ms를 더하지 않는다. DST 때문에 존재하지 않거나 두 번 존재하는 지역 날짜·시각을 datetime으로 변환할 때는 임의 offset을 고르지 않고 오류로 처리한다. 이미 offset이 명시된 datetime은 절대 시점이므로 이 모호성이 없다. 시간대 데이터 버전 차이에 따른 JS/Dart 결과도 T1의 적합성 대상으로 기록한다.
