# 리소스 셋과 브라우저 렌더링

2026-11-16 이관 기준의 확정 설계다. 패키지 역할과 공개 계약이 지켜야 할 의미를 다룬다. 현재 사용 가능한 API는 [호스트 연결 명세](07-host-integration.md), 선택의 배경은 [결정 이력](../history/resource-sets-browser-2026-11-16.md), 코드 기준점과 미결 사항은 [구현 인계](../handoff/resource-sets-browser-2026-11-16.md)를 따른다.

## 제품과 패키지 역할

Viewstem은 개인 프로젝트인 범용 선언형 UI 런타임이다. Core는 View 실행, State, Query, Action과 리소스 셋의 공통 기반을 담당한다. 회사·서비스·산업별 업무 규칙과 DOM·UI 프레임워크 의존성은 core 밖에 둔다.

리소스 셋은 서비스가 가져와 등록할 수 있는 재사용 리소스 묶음이다. 컴포넌트와 별개로 쓰는 Query·Action도 묶을 수 있다. 코드형 컴포넌트는 공개 정의와 실제 구현을 함께 제공할 수 있다. 선언형 리소스에는 별도 구현 코드가 필요하지 않을 수 있다. 누구나 공개 도구와 계약으로 자기 리소스 셋을 만들 수 있어야 한다.

| 패키지 또는 프리셋 | 확정 역할 |
|---|---|
| `@viewstem/core` | DOM과 프레임워크에 독립적인 View 실행, State, Query, Action 및 리소스 셋 공통 기반 |
| `@viewstem/dom` | 공통 브라우저 기반과 바닐라 DOM 컴포넌트 연결자. 두 역할을 패키지 내부에서 구분한다. |
| `@viewstem/svelte` | 공통 브라우저 기반을 이용하는 Svelte 컴포넌트 연결자와 Svelte 앱 편의 기능 |
| `@viewstem/ui` | 같은 공개 계약으로 작성하는 기본 DOM 컴포넌트 리소스 셋. Svelte 의존성을 두지 않는다. |
| Patchview | 서비스가 Viewstem을 직접 사용하면서 가져와 등록하는 회사 리소스 프리셋. 회사 레이아웃, PlantMap, ECharts, 업무 Action 등의 정의와 필요한 구현을 제공한다. |

공통 연결 계약만으로 제삼자가 React 연결자를 만들 수 있어야 한다. Viewstem의 초기 제공 연결자는 DOM과 Svelte다. `@viewstem/svelte`와 `@viewstem/ui`는 `@viewstem/dom`에 의존하고, DOM만 사용하는 앱은 Svelte 없이 실행한다. 설치 조합은 [설치 안내](../../apps/docs/src/content/docs/ko/docs/installation/index.md)를 따른다.

기본 UI는 일반 리소스 셋의 등록 규칙을 따른다. 서비스가 `@viewstem/ui` 셋을 직접 등록하거나, 이를 의존성으로 선언한 다른 셋을 등록할 때 함께 등록된다.

Svelte가 DOM 위에서 동작한다는 표현에서 DOM은 공통 브라우저 기반을 가리킨다. Svelte 코드는 Svelte 연결자가 맡고, 바닐라 DOM 코드는 DOM 연결자가 맡는다. 단일 View에서 DOM·Svelte·React 리소스를 섞는 것이 구조적 목표다. 사용하려는 리소스에 맞는 연결자와 구현이 등록되어야 하며 혼합 렌더링의 실행 적합성은 별도 검증이 필요하다.

## 셋 식별과 등록

- 셋 ID와 개별 리소스 ID는 별개다. 작성자가 리소스 ID를 명시하며 셋 이름 prefix를 자동 강제하지 않는다. 현행 Registry의 정의 식별은 [(kind, id)](../VIEWSTEM-SPEC.md#41-정의와-인스턴스)다. 셋 identity, 정의 계약의 identity, 구현 binding의 identity 및 관계는 일관되게 구체화한다.
- 셋은 이미 가져온 의존 셋을 참조할 수 있다. 상위 셋을 등록할 때 참조한 의존 셋을 순회해 함께 등록한다. 의존 참조는 런타임 다운로드나 설치를 요청하지 않는다.
- 같은 의존 셋을 여러 경로에서 만나면 한 번 등록하고 재사용한다. 같은 저장소에서 서로 다른 정의가 같은 `(kind, id)`를 사용하면 충돌 오류다. 서로 다른 종류의 정의는 같은 ID를 사용할 수 있다. 조용한 덮어쓰기, 마지막 등록 우선, 호환되지 않는 셋 버전의 임의 선택은 허용하지 않는다. 동일 셋의 판정, 버전 호환의 해석과 순환 검출 방식은 구현 설계에서 정한다.
- 중복·교체는 모든 리소스에 적용하는 공통 계약이다. DOM Button의 중복 등록과 독립 Query·Action 등록도 같은 규칙을 따른다. 첫 버전에서는 같은 저장소의 코드형 컴포넌트 ID 하나에 구현 하나를 연결한다. DOM 구현과 Svelte 구현을 함께 제공하려면 서로 다른 컴포넌트 ID로 등록한다. 같은 컴포넌트 ID에 서로 다른 구현을 일반 추가 등록으로 연결하려 하면 충돌 오류다.
- 의도적 교체는 `registry.replaceResource()`로 요청한다. 코드 Action의 동일 ID 교체는 입출력 계약과 필수 호스트 기능을 보존해야 한다. 일반적인 수정·삭제·hot-swap의 의미는 별도 범위다. [코드 Action의 교체 계약](04-action.md#코드-action-등록과-갱신)
- 등록 시도 전체를 원자적으로 공개한다. 의존 셋, 정의, 코드 Action과 컴포넌트 구현 연결 정보를 모두 검증하고 한꺼번에 게시한다. 실패하면 이번 시도가 추가한 항목은 하나도 남기지 않으며 이미 등록한 항목은 유지한다.
- 리소스 셋과 resolver가 가져온 정의를 같은 저장소에 게시할 때, 게시 직전에 최신 저장소를 기준으로 후보를 다시 검증한다. 같은 `(kind, id)`에 서로 다른 정의가 충돌하면 먼저 게시된 정의를 보존하고 뒤의 후보를 전체 거절한다. 서로 충돌하지 않는 후보의 변경은 모두 반영한다.

## 공통 저장소와 View 적용

첫 버전에서 각 Runtime은 기본으로 리소스 저장소 하나를 가지며, 그 Runtime의 View들이 이를 공유한다. 별도로 생성한 Runtime은 각각의 기본 저장소를 사용한다. 서비스가 여러 Runtime에 같은 리소스 저장소를 명시적으로 주입한 경우 해당 Runtime들이 그 저장소를 공유한다. 저장소의 소유와 접근 경계는 Runtime을 조립할 때 드러낸다. 한 Runtime에 여러 리소스 저장소를 두는 구성은 후속 범위다. 리소스 저장소와 State 값을 관리하는 StateStore는 별개다.

새 View는 생성 시 사용 가능한 리소스와 구현 설정을 기본으로 사용한다. 열린 View는 새 셋 등록에 자동 반응하지 않는다. 서비스가 적용 대상을 지정할 수 있어야 한다. 예를 들어 A View에 새 설정을 적용해도 B View는 자신이 사용 중인 설정을 유지한다. View가 사용하는 정의, 해당 컴포넌트 구현 및 코드 Action 함수는 함께 일관된 구성을 이뤄야 한다. 이전 정의를 사용하는 View가 공유 저장소에서 최신 구현 함수만 다시 조회해서는 안 된다.

열린 View에 리소스를 추가 적용할 때 기존 수명과 현재 State를 보존한다. 현재와 같은 정의 및 구현을 사용하는 노드는 기존 인스턴스를 유지한다. 적용 후보가 기존 정의·구현 또는 코드 Action 함수 연결의 변경을 요구하면 준비 단계에서 추가 적용을 거절한다.

추가 적용 시점에 이미 실행 중인 Query와 Action은 시작 당시의 리소스 정의와 구현으로 계속 실행한다. 추가 적용 뒤 새로 시작하는 독립 실행은 적용된 구성을 사용한다.

저장소에 명시적 교체가 게시되면 이후 생성하는 View는 교체된 리소스를 사용한다. 열린 View는 서비스가 해당 View에 교체를 명시적으로 적용할 때까지 기존 구성을 사용한다. 교체 적용에 성공하면 현행 `replace()`와 같이 해당 View의 내부 수명을 새로 시작하며 서비스 소유 State는 보존한다. [현행 교체 계약](07-host-integration.md#최소-sdk와-적용-완료)

대상 View의 설정은 View 단위로 한 번 확정한다. 같은 View를 여러 곳에 표시할 때 각 표시 연결은 그 설정을 사용하며, 렌더 완료와 실패는 표시 연결별로 관찰한다. 한 연결에서 렌더가 실패해도 확정된 View 설정과 다른 연결의 렌더 진행을 유지한다.

브라우저의 `mount().ready`는 View 준비와 표시 연결이 성립하면 View를 반환한다. `whenRendered()`는 해당 표시 연결에 실제 렌더가 완료됐는지 또는 실패했는지 보고한다. 첫 렌더에서 일부 컴포넌트가 실패해도 성립한 표시 연결과 정상 컴포넌트는 유지된다.

같은 View 적용에서 더 최신 투영이 현재 렌더할 투영을 대체하면, 해당 표시 연결의 미완료 렌더 대기는 최신 투영의 결과를 따른다. 대체된 투영의 늦은 오류는 무시하고 이미 끝난 대기의 결과는 유지한다. 새 View 적용이 확정되면 이전 적용에서 아직 끝나지 않은 대기는 `CANCELLED`가 된다. [현행 적용 완료 계약](07-host-integration.md#최소-sdk와-적용-완료)

| 작업 | 효과 |
|---|---|
| 리소스 셋 등록 | 해당 Runtime이 사용하는 저장소에 리소스를 추가한다. |
| View에 설정 적용 | 서비스가 지정한 View에서 사용할 리소스와 구현 구성을 반영한다. |
| View 정의 변경 | 원하는 컴포넌트 인스턴스를 배치하거나 변경한다. |

셋 등록과 View 설정 적용을 마쳐도 View 정의에서 참조하지 않은 PlantMap은 생성되지 않는다. 서비스는 리소스 설정과 View 정의 변경을 한 요청에 담을 수 있다. 이 경우 새 정의를 적용할 리소스 설정과 함께 검증하고, 준비가 성공하면 설정과 정의를 한 번에 확정한다.

View 설정의 준비·검증을 위해 호출한 콜백에서 Action을 요청하면 본문이 실행되기 전에 거절한다. 준비 중 기존 화면의 일반 클릭은 그 View에 이미 확정된 구성을 사용해 처리한다.

## 실패 경계

| 실패 단계 | 확정된 효과 |
|---|---|
| 셋 등록의 검증·준비 | 이번 등록의 변경을 공개하지 않고 기존 저장소를 유지한다. |
| 대상 View 설정·정의의 검증·준비 | 대상 View의 기존 설정과 정의를 유지한다. 이미 성공한 별도 저장소 등록과 다른 View는 영향을 받지 않는다. |
| 실제 컴포넌트 mount·render | 실패 이후 DOM·포커스·컴포넌트 로컬 상태의 완전 복구는 미확정이다. |

**D163 · 선언에 없는 참조와 값 대기의 구분.** 참조할 대상이 선언에 없다고 준비 단계에서 확인할 수 있으면 `PublicError.location`에 잘못된 참조의 선언 내 위치를 담아 오류를 반환한다. 예를 들어 View에 `count`를 선언하고 필수 Value 입력에 `/states/coutn`을 쓰면 첫 마운트의 `ready`가 거절된다. 열린 View에 적용할 때는 후보를 거절하고 기존 화면과 State를 유지한다. [공개 오류 계약](07-host-integration.md#공통-오류와-진단)

`/event`는 이벤트 핸들러의 Action `inputs`와 전달 `payload`에서 읽을 수 있다. 일반 노드 입력, `when`, `repeat`에서 쓰면 준비 단계에서 `REFERENCE_NOT_FOUND`와 위치를 반환한다.

선언된 State의 값이 아직 없고 해당 값이 노드 준비에 필요하면 그 노드를 대기 상태로 둔다. 독립적인 다른 노드는 계속 표시한다.

적용 후보의 View 정의에서 바로 표시할 컴포넌트에 필요한 구현 바인딩이 설정 후보에 빠져 있으면 준비 단계에서 적용을 거절한다. 설정 확정 후 조건이 바뀌어 처음 필요한 구현이 없거나 특정 표시 연결에서만 렌더할 수 없는 경우에는 해당 표시 연결의 렌더 실패로 보고한다.

렌더 실패를 특정 컴포넌트로 좁힐 수 있으면 영향은 해당 컴포넌트와 그 슬롯에 의존하는 자식에 한정한다. 독립적인 컴포넌트는 계속 렌더링한다. 실패한 표시 연결의 렌더 완료 대기에는 실패를 보고한다.

외부 API 호출의 효과는 위 원자성 범위에 속하지 않는다. 구체적 API와 적용 단위의 snapshot·version·buffer 방식, 렌더 오류 복구 전략은 [구현 인계](../handoff/resource-sets-browser-2026-11-16.md#미결-사항)에 남긴다.

## Headless 실행과 호스트 기능

렌더러 없이 서버에서 core 리소스를 등록하고 Action만 실행할 수 있어야 한다. 등록 자체의 유효성과 실제 View의 렌더 가능성을 별도로 판단한다. UI 구현을 조용히 누락하고 셋 전체가 등록됐다고 보고해서는 안 된다. View가 실제로 필요로 하는 컴포넌트의 구현·연결 누락은 [실패 경계](#실패-경계)에 따라 진단한다. 저장소에 등록되어 있어도 View가 사용하지 않는 UI의 렌더 가능성까지 요구하지 않는다.

논리적인 리소스 셋과 물리적인 패키지·entrypoint를 구별한다. 작성자는 core 정의·Action과 프레임워크 구현을 entrypoint 또는 패키지로 나눌 수 있다. 소비자는 자신의 실행 환경에 필요한 구성을 고른다. Headless의 설치·import 의존성과 번들 크기는 실제 배포 구조와 소비 경로에 달려 있다.

셋은 외부 기능에 대한 요구를 선언하고 서비스가 실제 router·API·데이터·인증 연결을 공급한다. 예를 들어 발전소 상세로 이동하는 Action은 routing capability를 요구하고 실제 router·경로·백엔드는 서비스가 연결한다.

호스트 기능이 아직 공급되지 않은 셋도 등록할 수 있다. Action 시작 직전에 그 Action이 요구하는 필수 호스트 기능을 확인하고, 빠진 기능이 있으면 실행 전에 오류를 반환한다. capability의 공개 표기와 서비스 주입 방식은 구현 설계에서 정한다.

Viewstem은 서비스가 신뢰해 직접 가져온 셋·연결자 코드만 실행한다. View JSON의 코드형 리소스 참조는 이미 등록된 구현으로 해석한다. 해당 구현이 미등록이면 실패 경계에 따라 오류를 반환한다. 선언형 정의의 resolver 경로는 현행 호스트 계약을 따른다. [실패 경계](#실패-경계) · [호스트 설정과 resolver](07-host-integration.md#최소-sdk와-적용-완료)

## 혼합 트리의 소유권

- 부모 구현은 자식이 놓일 콘텐츠 영역이나 slot을 제공한다. 자식 연결자는 그 안에서 해당 인스턴스를 생성·갱신·파괴한다.
- 부모의 렌더가 성공적으로 끝난 시점에 제공되지 않은 슬롯의 자식은 이번 표시에서 빠진다. 렌더 완료 대기는 실제로 표시할 나머지 노드를 기준으로 끝낸다. 부모가 나중에 슬롯을 제공하면 그때 자식을 마운트한다.
- 공통 브라우저 기반은 하나의 View를 기준으로 Viewstem 자식의 정체성, 순서, 연결, 이동·교체·해제를 조정한다. 각 부모는 자식 소유 영역을 임의로 다시 쓰지 않으며, 공통 기반은 Svelte·React 등 구현 내부 DOM을 직접 고치지 않는다. 자식 컴포넌트를 위해 전체 View 렌더러를 다시 실행하지 않는다.
- 같은 슬롯 안에서 같은 수명의 자식 순서만 바뀌면 렌더 인스턴스를 유지한다. 부모가 슬롯 DOM을 교체하면 기존 자식 렌더 인스턴스를 한 번 정리한 뒤 새 슬롯에 다시 마운트한다. Viewstem 노드 수명이 같으면 다시 마운트하더라도 core State는 보존한다.
- 이미 표시한 노드의 필수 입력이 대기 상태가 되면, 노드 수명과 슬롯이 같은 동안 렌더 인스턴스를 유지하고 대기 상태를 표시한다. 해당 노드에서 새 Action을 시작하는 이벤트는 거절한다. 입력이 준비되면 유지한 인스턴스에 새 입력을 반영한다.
- 대기 중에 철회되거나 교체된 슬롯의 자식 정리도 렌더 완료 대기에 포함한다. 대기 중 새 슬롯 제공은 기억하고, 입력이 준비된 뒤 그 슬롯의 자식을 마운트한다.
- 컴포넌트 이벤트로 Action을 시작하려는 시점에, 이벤트를 보낸 표시 연결과 렌더 인스턴스가 여전히 유효하고 이벤트의 노드 수명과 구현 연결이 현재 View와 일치해야 한다.
- 한 core View의 State·Action·이벤트 공유와 프레임워크 native context 전파는 계약이 다르다. DOM 경계를 넘는 Svelte native context 전파는 미확정이며 향후 지원 여부도 열려 있다.
- 1차 검증은 Svelte Layout 안의 DOM Button, DOM Card 안의 Svelte PlantMap 또는 Chart를 기준으로 한다. 임의 중첩과 프레임워크별 기능 전체의 지원은 이 사례에서 일반화하지 않는다. Menu·Trigger의 결합, `table`·`select`의 DOM 의미, 직접 자식 CSS와 wrapper, portal, SSR·hydration, context·transition의 상세 동작은 별도 범위다. [수락 시나리오](../handoff/resource-sets-browser-2026-11-16.md#후속-수락-시나리오)

코드 Component의 구현 바인딩을 보존하는 갱신은 포트·슬롯·이벤트의 해석된 계약을 유지한다. 직접 계약 변경과 참조 Type 변경에 같은 기준을 적용한다. 다른 계약에 맞춘 새 구현을 게시하려면 계약과 바인딩을 `replaceResource({ component })`로 함께 교체한다. 새 View와 명시적으로 교체를 적용한 열린 View에 새 조합을 사용한다.

독립 셋 패키지는 앱과 같은 Core 모듈 인스턴스에서 셋을 정의한다. 앱 쪽에 해석되도록 Core를 peer dependency로 선언하고 해당 패키지 번들에서 외부화한다.

## UI 셋의 스타일 소유권

**D169.** 브라우저 UI 셋은 자신이 만든 DOM에 기본 스타일을 적용한다. 소유 표시가 붙은 조상 아래에 있더라도, 슬롯에 들어온 외부 요소의 기본 외형은 해당 요소의 셋이 정한다. 일반 CSS 상속과 호스트가 서로 연결한 테마 변수는 기존 브라우저 규칙을 따른다.

DOM 작성자는 `@viewstem/dom/styles`의 `createStyleScope(id)`와 `@viewstem/dom/styles/postcss`의 `scopeUiCss(id)`를 같은 셋 식별자로 사용할 수 있다. 도구는 CSS 규칙의 최종 대상에 소유 조건을 적용한다. 기존 `data-viewstem-ui`는 이전 테마 변수를 읽는 범위다. [설계 초안](../designs/viewstem-ui-set-policy-review-2026-11-19/design_draft.md)

서로 다른 셋 ID로 빌드한 스타일은 CSS 레이어, 애니메이션, 내부 CSS 변수 이름을 공유하지 않는다. `publicProperties`로 지정한 테마 변수는 원래 이름을 유지한다. 컴포넌트가 JavaScript에서 내부 CSS 변수를 갱신할 때는 `createStyleScope(id).localProperty(name)`으로 빌드와 같은 이름을 얻는다.

**D170.** `@viewstem/ui`의 `browser` 진입점은 셋과 기본 CSS를 함께 불러온다. 이 조건을 선택하는 브라우저 번들러에서는 다른 셋을 통해 간접으로 가져올 때도 CSS가 포함된다. Node는 셋 정의를 내보내는 JS 진입점을 사용한다. 스타일시트를 직접 불러오는 호스트는 `@viewstem/ui/styles.css`를 사용한다. Registry 등록은 셋의 리소스를 게시한다.

## Svelte 어댑터 입력 타입

**D162 · 등록 계약에서 Svelte 입력 타입 추론.** 어댑터는 `ComponentAdapterProps<typeof contract>`로 Component 계약의 포트에서 입력 타입을 추론한다. TypeScript에서 `svelteComponent(contract, implementation)`으로 바인딩을 만들 때 구현의 props 타입이 같은 계약과 일치하는지 검사한다. 타입 인자 없는 `ComponentAdapterProps`도 공통 어댑터에서 사용할 수 있다.

- `node.status === 'ready'`로 좁히면 `node.inputs`의 필수 `Value` 포트 값은 존재한다. 선택 포트 값은 생략될 수 있다.
- `node.status === 'pending'`이면 필수 포트의 입력도 없을 수 있다. 이미 표시한 같은 노드에는 이전에 표시한 값이 남을 수 있다. 값이 남아 있어도 준비 여부는 `node.status`로 확인한다.
- `State` 포트는 `StateHandle<T>`를 전달한다. 필수 핸들의 `read()` 결과도 값이 없으면 `undefined`일 수 있다.

### 연결자 자체의 렌더 완료

**D161 · 연결자 렌더 완료 메서드의 선택화.** `MountedComponent.whenRendered(signal)`은 선택 메서드다. 생략하면 렌더러는 연결자 자체의 DOM 반영이 `mount()`, `update()` 또는 `setPending()` 호출에서 동기로 끝났다고 간주한다. 비동기 반영을 하는 연결자는 이 메서드에서 해당 렌더 작업의 완료나 실패를 알린다. 표시 연결의 `whenRendered()`는 연결자 자체의 반영과 실제로 제공된 슬롯 자식의 반영을 기다린다.

`update()`, `setPending()`, `dispose()`는 필수다. 필수 입력이 대기 상태가 되면 같은 인스턴스에 대기 상태를 표시하고, 표시 연결이 끝나면 연결자의 정리 완료를 기다린다.

연결자 또는 fallback의 렌더 콜백에서 표시 연결을 닫으면 다음 렌더 콜백을 시작하지 않는다. 이미 시작한 콜백이 반환한 핸들은 연결 종료 중에 정리한다.
